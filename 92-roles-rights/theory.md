# Теория. Роли и права на объекты

## Какую задачу мы решаем

После занятия 91 в базе есть администратор, который может всё, и кладовщик Петров, который не может ничего. Рабочая жизнь между этими крайностями.

Кладовщик принимает материалы и выдаёт их на объекты: создаёт и проводит поступления и передачи, смотрит остатки. Заявки ему нужно читать — по ним он принимает груз, — но создавать заявки и согласовывать их не его дело. Цены он видит в отчёте, но менять не должен: цены устанавливает снабжение.

Снабженец ведёт заявки и цены, смотрит все отчёты, но не проводит складские документы: материал физически принимает и выдаёт кладовщик, и только он отвечает за то, что лежит на складе.

Нужно описать эти обязанности так, чтобы платформа сама не давала сделать лишнее.

## Права на объект

Для каждого объекта конфигурации роль хранит свой набор прав. Набор зависит от вида объекта.

| Объект | Типичные права |
| --- | --- |
| Справочник | Чтение, Добавление, Изменение, Удаление, Просмотр, Интерактивное добавление, Редактирование, Интерактивная пометка удаления, Ввод по строке |
| Документ | то же, плюс Проведение, Отмена проведения, Интерактивное проведение, Интерактивная отмена проведения, Интерактивное изменение проведённых |
| Регистр | Чтение, Изменение, Просмотр, Редактирование |
| Отчёт, обработка | Использование, Просмотр |
| Подсистема | Просмотр |

## Основные и интерактивные права

Права делятся на две группы, и путать их нельзя.

**Основные права** — **Чтение**, **Добавление**, **Изменение**, **Удаление**, **Проведение** — проверяются при **любом** обращении к данным: из формы, из кода, из отчёта, из запроса. Без **Чтения** справочника запрос к нему завершится ошибкой, даже если запрос выполняется в общем модуле.

**Интерактивные права** — **Просмотр**, **Редактирование**, **Интерактивное добавление**, **Интерактивное проведение** и другие с приставкой «Интерактивное» — разрешают действие **пользователю в интерфейсе**: увидеть список в разделе, открыть форму для правки, нажать **Создать** или **Провести**.

Интерактивное право невозможно без основного: нельзя редактировать то, что нельзя изменить. Поэтому в редакторе роли платформа сама отмечает зависимые права. Отметили **Редактирование** — отметятся **Изменение** и **Просмотр**.

А вот основное право без интерактивного встречается часто, и это важный приём. Кладовщику нужно **Изменение** регистра `ОстаткиМатериалов`: при проведении передачи код записывает движения в регистр от его имени. Но **Редактирования** регистра у него нет: открыть движения и поправить их руками он не сможет. Писать в регистр может только проведение документа.

## Роль по функции, а не по человеку

Можно сделать роль «Петров» и отметить в ней всё, что нужно Петрову. Через год Петров станет старшим кладовщиком и начнёт ещё и согласовывать заявки; появится второй кладовщик; Петров уволится. Каждый раз придётся править роль — и вспоминать, что в ней для чего.

Роли строят **по функциям**: «Кладовщик» — права на складские документы, «Снабженец» — на заявки и цены. Пользователю назначают **несколько ролей**, и его права — **объединение** прав всех его ролей. Если право есть хотя бы в одной роли, оно есть у пользователя. Запретить право, выданное другой ролью, нельзя: роли только добавляют.

Отсюда два правила.

1. **Общее — в базовую роль.** Права, которые нужны всем, — запуск тонкого клиента, сохранение своих настроек, печать, чтение справочников, просмотр разделов — собирают в роль `БазовыеПрава` и назначают каждому пользователю. Тогда роль «Кладовщик» описывает только то, что отличает кладовщика.
2. **Минимум прав.** В роль добавляют то, без чего человек не может выполнить свои обязанности, и не больше. Лишнее право однажды будет использовано по ошибке.

## Права для отчётов и форм

Отчёт на системе компоновки читает данные с правами пользователя. Отчёту `ОстаткиНаСкладах` нужны **Чтение** регистра `ОстаткиМатериалов` и регистра `ЦеныМатериалов`: без второго отчёт не построится у кладовщика, потому что набор данных `Цены` (занятие 73) прочитать нельзя. Права на сам отчёт — **Использование** и **Просмотр** — только открывают к нему дверь.

То же с командами и вводом на основании. Чтобы кладовщик мог создать поступление на основании заявки, ему нужно **Чтение** заявки и **Интерактивное добавление** поступления. Код `ОбработкаЗаполнения` читает заявку от его имени.

Раздел приложения пользователь видит, если у него есть **Просмотр** подсистемы и хотя бы одного объекта в ней. Раздела **Разработка** не будет ни у кого, кроме администратора: его просмотра нет ни в одной роли.

## Где живёт логика

| Что | Где | Почему |
| --- | --- | --- |
| Права, нужные всем | роль `БазовыеПрава` | одно место для общего |
| Права склада | роль `Кладовщик` | описывает функцию, а не человека |
| Права снабжения | роль `Снабженец` | то же |
| Кто какую функцию выполняет | роли, назначенные пользователю администратором | меняется без правки конфигурации |
| Запись движений от имени кладовщика | основное право **Изменение** регистра без интерактивного | писать может только проведение |

## Что важно запомнить

1. Роль хранит права на каждый объект; набор прав зависит от вида объекта.
2. Основные права проверяются при любом обращении к данным, включая код и отчёты; интерактивные — только действия пользователя в интерфейсе.
3. Интерактивное право требует основного, платформа отмечает зависимые права сама; основное право без интерактивного — приём «писать только через документ».
4. Роли строят по функциям; права пользователя — объединение прав всех его ролей, и роль не может отнять право, выданное другой.
5. Общие права собирают в базовую роль; в остальные роли добавляют минимум, нужный для обязанностей.
6. Отчёт читает данные с правами пользователя, поэтому ему нужны права на все таблицы его наборов данных.
