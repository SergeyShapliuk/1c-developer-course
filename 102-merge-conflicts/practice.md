# Практика. Правило Орлова и ваше правило в одном модуле

## Перед началом

Запустите конфигуратор учебной базы под пользователем «Администратор» и выгрузите базу в новый файл `.dt`: сегодня конфигурация базы будет заменена загрузкой из файлов.

Понадобится репозиторий `construction-erp` в ветке `feature/closed-sites` с тремя коммитами занятия 101. Каталог, в котором лежат `construction-erp` и конспект, ниже называется **рабочим каталогом курса**.

Орлова будете играть вы сами, во втором клоне. Чтобы не путаться, держите открытыми два окна терминала: одно в `construction-erp`, другое — с шага 2 — в `construction-erp-orlov`. Своей базы у Орлова в учебной практике не будет: он правит текст модуля прямо в файле, как это делают разработчики, работающие с модулями во внешнем редакторе.

## Шаг 1. Создайте сервер команды

В терминале перейдите в рабочий каталог курса — на уровень выше `construction-erp` — и создайте голый репозиторий:

```bash
git init --bare server/construction-erp.git
```

Теперь перейдите в `construction-erp`, подключите сервер и отправьте на него обе ветки:

```bash
cd construction-erp
git remote add origin ../server/construction-erp.git
git push -u origin main
git push -u origin feature/closed-sites
git remote -v
git branch -a
```

Адрес сервера — относительный путь к каталогу: Git работает с репозиторием на диске так же, как с репозиторием в интернете. Ключ `-u` связывает локальную ветку с веткой сервера, и дальше достаточно писать `git push` и `git pull` без параметров. `git branch -a` показывает и ваши ветки, и ветки сервера `remotes/origin/...`.

**Проверка:** `git remote -v` показывает `origin`, `git branch -a` показывает `remotes/origin/main` и `remotes/origin/feature/closed-sites`.

## Шаг 2. Создайте клон Орлова

Откройте второе окно терминала в рабочем каталоге курса:

```bash
git clone server/construction-erp.git construction-erp-orlov
cd construction-erp-orlov
git config user.name "Орлов Дмитрий"
git config user.email "orlov@example.com"
git log --oneline --all
```

`git clone` создаёт полную копию общего репозитория вместе с историей. Настройки `user.name` и `user.email` заданы **без** ключа `--global`: они действуют только в этом клоне, и коммиты Орлова будут подписаны его именем, а ваши — вашим.

**Проверка:** клон создан, `git log --oneline --all` показывает коммит `main` и три коммита `origin/feature/closed-sites`.

## Шаг 3. Орлов делает свою задачу

Во втором окне создайте ветку Орлова от `main`:

```bash
git switch -c feature/no-future-transfers
```

1. Откройте в «Блокноте» файл `src/cf/Documents/ПередачаМатериалов/Ext/ObjectModule.bsl` клона Орлова. Это версия `main`: проверки завершённого объекта в ней нет.
2. Найдите в `ОбработкаПроведения` блок с сообщением «Не указан объект строительства» и сразу после его `КонецЕсли;` вставьте проверку Орлова. Отступы — табуляцией, как в конфигураторе:

```bsl
	Если Дата > КонецДня(ТекущаяДатаСеанса()) Тогда
		Сообщение = Новый СообщениеПользователю;
		Сообщение.Текст = "Дата передачи в будущем: материалы передают по факту, а не заранее";
		Сообщение.Поле = "Дата";
		Сообщение.УстановитьДанные(ЭтотОбъект);
		Сообщение.Сообщить();
		Отказ = Истина;
	КонецЕсли;
```

`ТекущаяДатаСеанса()` возвращает текущую дату с учётом часового пояса сеанса; `КонецДня` даёт последнюю секунду сегодняшнего дня. Передача сегодняшним числом проходит, завтрашним — нет.

3. Сохраните файл. «Блокнот» сохраняет его в той же кодировке, в которой открыл.
4. Закоммитьте и отправьте ветку:

```bash
git diff
git add src/cf/Documents/ПередачаМатериалов/Ext/ObjectModule.bsl
git commit -m "Refuse future-dated transfers"
git push -u origin feature/no-future-transfers
```

**Проверка:** на сервере есть ветка `feature/no-future-transfers` с коммитом Орлова.

## Шаг 4. Орлов сливает задачу в main

Считаем, что задачу Орлова уже проверили и одобрили, — как это делают, разберём на занятиях 103 и 104. Во втором окне:

```bash
git switch main
git merge feature/no-future-transfers
git push
git log --oneline --graph --all
```

Git сообщает `Fast-forward`: в `main` после ответвления ветки не было новых коммитов, и Git просто передвинул `main` на коммит Орлова. Коммита слияния не появилось. `git push` отправил новый `main` на сервер.

**Проверка:** в `main` клона Орлова и на сервере два коммита — коммит занятия 100 и `Refuse future-dated transfers`.

## Шаг 5. Подготовьтесь к получению изменений

Вернитесь в первое окно, в `construction-erp`. Прежде чем что-то получать, убедитесь, что база и ваша ветка совпадают.

1. Выгрузите конфигурацию учебной базы в `src\cf`.
2. Выполните `git status`. Изменений быть не должно: всё сделанное на занятии 101 уже в коммитах. Если изменения есть, разберитесь с ними, как на шаге 7 занятия 101, и закоммитьте нужное.
3. Получите изменения с сервера и посмотрите на историю:

```bash
git fetch
git log --oneline --graph --all
```

`origin/main` ушёл вперёд на коммит Орлова, а ваша ветка ответвилась от старого `main`. История разошлась на две линии.

**Проверка:** выгрузка не дала изменений, `git log --graph` показывает две линии: ваши три коммита и коммит Орлова.

## Шаг 6. Слейте main в свою ветку

Сначала обновите свой локальный `main`. При переключении ветки Git меняет файлы, но не базу, поэтому базу сейчас не трогаем.

```bash
git switch main
git pull
git switch feature/closed-sites
git merge main
```

`git pull` в `main` проходит перемоткой. А `git merge main` в вашей ветке останавливается: Git сообщает `CONFLICT (content): Merge conflict in src/cf/Documents/ПередачаМатериалов/Ext/ObjectModule.bsl` и просит разрешить конфликт, а затем закоммитить результат.

Вы и Орлов вставили код в одно и то же место — сразу после проверки объекта строительства.

**Проверка:** слияние остановлено конфликтом в `ObjectModule.bsl`, `git status` показывает этот файл как изменённый обеими сторонами.

## Шаг 7. Разрешите конфликт

1. Откройте `ObjectModule.bsl` в «Блокноте» и найдите маркеры `<<<<<<<`, `=======`, `>>>>>>>`. Между первым и вторым — ваша проверка завершённого объекта, между вторым и третьим — проверка Орлова.
2. Решите по смыслу: нужны обе проверки, у них разные заказчики. Оставьте обе — сначала проверку завершённого объекта, затем проверку даты, — и удалите три строки маркеров.
3. Перечитайте процедуру `ОбработкаПроведения` сверху вниз: склад, объект строительства, завершённый объект, дата, пустая табличная часть, строки, ранний `Возврат`, движения, контроль остатков. Маркеров не осталось.
4. Завершите слияние:

```bash
git add src/cf/Documents/ПередачаМатериалов/Ext/ObjectModule.bsl
git commit --no-edit
git log --oneline --graph
```

`git commit --no-edit` создаёт коммит слияния с сообщением, которое Git предложил сам: `Merge branch 'main' into feature/closed-sites`. На графе видно, как две линии сошлись в этом коммите.

**Проверка:** в модуле обе проверки и ни одного маркера; в истории ветки есть коммит слияния с двумя родителями.

## Шаг 8. Загрузите результат в базу

Сейчас файлы ветки содержат оба правила, а база — только ваше. **Не выгружайте конфигурацию**: выгрузка перезаписала бы результат слияния версией из базы, и правило Орлова пропало бы из файлов.

1. В конфигураторе учебной базы выполните **Конфигурация → Загрузить конфигурацию из файлов** из каталога `src\cf` и подтвердите замену конфигурации.
2. Выполните `F7`.
3. Откройте модуль объекта `ПередачаМатериалов` и найдите в `ОбработкаПроведения` обе проверки.

**Проверка:** в модуле объекта передачи в базе обе проверки, синтаксический контроль ошибок не находит.

## Шаг 9. Проверьте оба правила

Запустите приложение под администратором.

1. Создайте передачу с «Центрального склада» на «ЖК Северный», «Песок речной» — `1`, датой **завтрашнего** дня. Нажмите **Провести**; если платформа спросит о неоперативном проведении, подтвердите. Проведение отклонено, сообщение о дате в будущем стоит у поля даты.
2. Поставьте сегодняшнюю дату и смените объект на «ЖК Восточный», завершённый на занятии 101. Проведите. Отклонено с сообщением о завершённом объекте.
3. Верните «ЖК Северный» и проведите. Документ проведён.
4. Отмените проведение и пометьте передачу на удаление.

Вернитесь в конфигуратор, выгрузите конфигурацию в `src\cf` и выполните `git status`. Изменений нет: база и ветка совпадают.

**Проверка:** оба правила работают, обычная передача проводится, контрольная выгрузка не показывает изменений.

## Шаг 10. Отправьте ветку на сервер

```bash
git push
```

Во втором окне, у Орлова, получите изменения и посмотрите, что видит коллега:

```bash
git fetch
git log --oneline --graph --all
```

Орлов видит вашу ветку вместе с коммитом слияния: ваша работа уже учитывает его правило. Когда ветка попадёт в `main` (занятие 103), его `main` получит её перемоткой.

**Проверка:** на сервере ветка `feature/closed-sites` содержит коммит слияния; в клоне Орлова он виден после `git fetch`.

## Проверка результата

Занятие пройдено, если выполняются шесть условий:

1. Есть голый репозиторий `server/construction-erp.git` и клон `construction-erp-orlov` с коммитами, подписанными Орловым.
2. `main` на сервере содержит коммит `Refuse future-dated transfers`, слитый перемоткой.
3. Ветка `feature/closed-sites` содержит коммит слияния с `main`; конфликт в `ObjectModule.bsl` разрешён, маркеров нет.
4. В базе разработки загружена конфигурация ветки: передача не проводится ни на завершённый объект, ни будущей датой, обычная передача проводится.
5. Контрольная выгрузка после загрузки не показывает изменений.
6. Вы можете объяснить, почему конфигурацию выгружают до слияния и загружают после.

## Контрольные вопросы

Не подглядывая в теорию, ответьте устно или в заметках:

1. Чем голый репозиторий отличается от обычного и почему на сервере команды он голый?
2. Чем `git fetch` отличается от `git pull`?
3. В каком случае слияние проходит перемоткой, а в каком создаёт коммит слияния?
4. Почему Git не смог слить ваши изменения сам и как вы решили, какой вариант оставить?
5. Что случилось бы с правилом Орлова, если бы после слияния вы сначала выгрузили конфигурацию, а не загрузили?
6. Обе проверки — завершённого объекта и даты — живут в `ОбработкаПроведения` модуля объекта передачи. Почему проверку даты нельзя было ограничить формой передачи и почему её место среди проверок документа, до формирования движений?

Сверьте ответы с [теорией](theory.md). Если на каждый вопрос получается ответить одним-двумя предложениями, переходите к занятию 103.
