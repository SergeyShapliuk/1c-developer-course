# Теория. Двое правят один модуль

## Какую задачу мы решаем

В отдел разработки пришёл второй разработчик — Орлов Дмитрий. Ему досталась задача главного бухгалтера: передачу материалов нельзя оформлять будущей датой, выдачу оформляют по факту. Его правило живёт там же, где ваше, — в `ОбработкаПроведения` передачи, среди проверок документа.

У каждого из вас своя база разработки. Если просто переписать модуль из одной базы в другую, правило того, кто копировал первым, потеряется. Нужен способ собрать два изменения одного модуля так, чтобы сохранились оба, и чтобы было видно, кто и что сделал.

## Удалённый репозиторий команды

На занятии 10 удалённым репозиторием был GitHub. Для командной работы важна не сама площадка, а то, что у команды есть **один общий репозиторий**, через который все обмениваются коммитами. В учебных целях его можно сделать прямо на диске.

**Голый репозиторий** (bare) — репозиторий без рабочего каталога: в нём есть только история, файлов для правки нет. Создаёт его команда `git init --bare`. Так устроены репозитории на любом сервере: в них никто не работает напрямую, туда только отправляют и оттуда только получают.

Каждый разработчик делает **клон** — свою полную копию общего репозитория — командой `git clone`. У клона общий репозиторий автоматически записан под именем `origin`.

```text
ваша база разработки
   ⇅  выгрузка / загрузка
construction-erp — ваш клон
   ⇅  push / fetch
server/construction-erp.git — общий голый репозиторий
   ⇅  push / fetch
construction-erp-orlov — клон Орлова
   ⇅  выгрузка / загрузка
база разработки Орлова
```

Схема читается от краёв к центру. Изменение рождается в базе разработчика, выгрузкой попадает в его репозиторий, отправкой — на сервер. Обратный путь — получение с сервера, слияние и загрузка в базу.

## Отправка и получение

| Команда | Что делает |
| --- | --- |
| `git push` | отправляет коммиты текущей ветки на сервер |
| `git fetch` | забирает с сервера новые коммиты всех веток, не трогая ваши ветки и файлы |
| `git pull` | `fetch` и сразу слияние полученного в текущую ветку |

После `git fetch` ветки сервера видны локально под именами `origin/main`, `origin/feature/...`. Это ваша копия того, что было на сервере в момент получения. Смотреть их можно командой `git log --oneline --all --graph`: ключ `--graph` рисует ветви истории линиями.

## Слияние

**Слияние** — объединение истории двух веток командой `git merge`. Возможны два случая.

**Перемотка** (fast-forward). В текущей ветке нет своих новых коммитов, а в сливаемой есть. Тогда Git просто передвигает указатель ветки вперёд, нового коммита не появляется. Так происходит, когда Орлов сливает свою ветку в `main`, в которой с момента ответвления ничего не менялось.

**Коммит слияния.** В обеих ветках есть свои коммиты. Git находит общего предка, сравнивает с ним изменения обеих сторон и создаёт коммит слияния с двумя родителями. Если стороны меняли разные места файлов, Git сольёт их сам.

## Конфликт

**Конфликт слияния** возникает, когда обе стороны изменили одно и то же место одного файла. Git не знает, какое изменение правильное, — возможно, нужны оба, возможно, одно из них лишнее. Он останавливает слияние и помечает спорное место **маркерами конфликта**:

```bsl
<<<<<<< HEAD
	Если ЗначениеЗаполнено(ОбъектСтроительства) И ОбъектСтроительства.Завершен Тогда
		// ... ваша проверка ...
	КонецЕсли;
=======
	Если Дата > КонецДня(ТекущаяДатаСеанса()) Тогда
		// ... проверка Орлова ...
	КонецЕсли;
>>>>>>> main
```

Между `<<<<<<< HEAD` и `=======` — версия текущей ветки, между `=======` и `>>>>>>>` — версия сливаемой. **Разрешить конфликт** — отредактировать файл так, как он должен выглядеть после слияния, убрать маркеры, добавить файл в индекс и завершить слияние коммитом.

Конфликт разрешают по смыслу, а не механически. Здесь обе проверки нужны — заказчики у них разные, и одна не заменяет другую. Значит, в файле останутся обе. В другом случае правильным будет взять одну сторону или написать третий вариант. Если смысл чужого изменения непонятен, его автора спрашивают, а не угадывают.

## Конфликт в XML

С модулями всё просто: файл `.bsl` — обычный текст, и конфликт в нём разрешает человек. С файлами метаданных и форм иначе. В `Form.xml` у каждого элемента есть внутренние идентификаторы и ссылки между элементами, и две правки, слитые построчно, легко дают файл, который платформа не загрузит или загрузит с испорченной формой.

Поэтому конфликт в XML разрешают так: берут одну сторону целиком, загружают её в базу и **повторяют в конфигураторе** изменение другой стороны, затем выгружают. Команды договариваются и заранее: одну форму в один момент правит один разработчик. На занятии 105 вы увидите хранилище конфигурации, которое делает такую договорённость правилом платформы.

## Порядок работы с базой

Git сливает файлы, но о базе ничего не знает. Поэтому слияние в 1С-проекте всегда обрамлено двумя действиями с базой.

1. **До слияния** — выгрузить конфигурацию и закоммитить всё своё. Если выгрузить после слияния, выгрузка перезапишет результат слияния старой версией из базы: в базе-то правила коллеги нет.
2. **Слить** — `git pull` или `git merge`, при конфликте разрешить.
3. **После слияния** — загрузить конфигурацию из файлов, выполнить `F7` и проверить работу в приложении.
4. **Контроль** — ещё раз выгрузить. Если `git status` чист, база и репозиторий совпадают.

Перед загрузкой, как всегда, нужна свежая резервная копия базы.

## Где живёт логика

| Правило | Автор | Где |
| --- | --- | --- |
| Передача на завершённый объект не проводится | вы | `ОбработкаПроведения` передачи, среди проверок документа |
| Передача будущей датой не проводится | Орлов | там же |
| Оба правила вместе | результат слияния | одна процедура в `ObjectModule.bsl` ветки, затем загрузка в базу |

## Что важно запомнить

1. Командная работа идёт через один общий репозиторий; на сервере он голый, у каждого разработчика — свой клон.
2. `git push` отправляет, `git fetch` получает без слияния, `git pull` получает и сливает.
3. Слияние без своих коммитов — перемотка; с коммитами с обеих сторон — коммит слияния.
4. Конфликт — когда обе стороны изменили одно место; Git ставит маркеры и ждёт решения человека.
5. Конфликт разрешают по смыслу; непонятное чужое изменение уточняют у автора.
6. Конфликт в XML форм и метаданных не сливают руками: берут одну сторону и повторяют другую в конфигураторе.
7. Слияние обрамлено действиями с базой: выгрузить и закоммитить до, загрузить и обновить после, выгрузить для контроля.
