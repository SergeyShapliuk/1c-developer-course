# Теория. Захватить, изменить, поместить

## Какую задачу мы решаем

На занятиях 101–104 командная работа шла через Git: каждый правил свою базу, выгружал её в файлы, а Git сливал изменения. На первой работе вы с большой вероятностью встретите другой порядок. Вам скажут: «Подключись к хранилищу, захвати справочник складов, добавь телефон, помести с комментарием». Многие команды, особенно те, что дорабатывают типовые конфигурации в конфигураторе, работают именно так, и у этого есть причины.

Вспомните конфликт в XML формы (занятие 102). Git не умеет надёжно слить две правки одной формы, и команда вынуждена договариваться, кто правит форму сейчас. Хранилище конфигурации делает такую договорённость правилом платформы: объект в каждый момент может править только один разработчик.

## Хранилище конфигурации

**Хранилище конфигурации** — общее место хранения конфигурации и всех её версий, встроенное в платформу. Каждый разработчик работает в своей базе, **подключённой** к хранилищу. Хранилище знает, у кого какой объект на редактировании, и хранит историю: кто, когда и с каким комментарием изменил конфигурацию.

Хранилище бывает файловым — каталог на диске или в общей папке сети — или работает через **сервер хранилища** по сети. Работа с ним в конфигураторе от этого не меняется.

У хранилища свои пользователи. **Пользователь хранилища** — не то же самое, что пользователь информационной базы (занятие 91): это учётная запись разработчика в хранилище, с правами на захват и помещение. **Администратор хранилища** заводит пользователей и задаёт их права.

## Цикл работы

Работа с хранилищем идёт по одному циклу.

1. **Получить** актуальную конфигурацию из хранилища — чтобы начать с последней версии.
2. **Захватить** объекты, которые нужно изменить. Захваченный объект можно править в своей базе; остальные открыты только для чтения.
3. **Изменить** объекты и проверить изменение в своей базе.
4. **Поместить** изменённые объекты в хранилище с комментарием. Помещение создаёт новую версию хранилища и снимает захват.

Пока объект захвачен, никто другой захватить его не может. Конфигуратор покажет, кем он захвачен, — с этим человеком и договариваются.

Если изменение не получилось, **отмена захвата** возвращает объект в состояние хранилища: все правки в нём пропадают, захват снимается.

## Захват корня

Добавление нового объекта — справочника, документа, роли — меняет не только сам объект, но и состав конфигурации. Поэтому для этого нужно захватить **корень конфигурации**. Пока корень захвачен одним разработчиком, другой не может добавить новый объект. В больших командах это узкое место, и новые объекты стараются добавлять быстро и помещать сразу.

## Комментарий версии

Комментарий при помещении играет ту же роль, что сообщение коммита: он отвечает, что изменено и зачем. Через полгода история хранилища с комментариями «Правки», «111» и пустыми строками так же бесполезна, как история Git с сообщениями `fix`. Во многих командах в комментарий пишут номер задачи.

## История хранилища

**История хранилища** — список версий: номер, автор, дата, комментарий. Для каждой версии можно посмотреть, какие объекты изменились, сравнить её с предыдущей или с текущей конфигурацией, получить конфигурацию этой версии в файл. Это ответ на тот же вопрос, что и история Git: что изменилось, когда, кто и зачем.

## Хранилище и Git

| Вопрос | Git | Хранилище конфигурации |
| --- | --- | --- |
| Как двое правят одно место | оба правят, потом слияние | второй ждёт, пока первый поместит |
| Конфликты | бывают, разрешает человек | слияния нет, поэтому и конфликтов слияния нет |
| Формы и метаданные | слияние XML опасно, нужна договорённость | захват объекта — правило платформы |
| Ветки | сколько угодно | одна линия версий |
| Ревью до слияния | pull request | встроенного нет |
| Где работает | любой текст, любые инструменты | только в конфигураторе |

Ни один способ не лучше во всём. Хранилище проще и безопаснее для форм и метаданных, но не даёт веток и ревью и заставляет ждать. Git даёт ветки, ревью и автоматические проверки, но требует дисциплины выгрузки, загрузки и разрешения конфликтов.

Поэтому способы часто совмещают. Инструменты вроде **GitSync** по расписанию выгружают каждую новую версию хранилища в коммит Git с автором и комментарием: команда работает в хранилище, а история, поиск по коду и ревью — в Git. Среда **1С:EDT** работает с Git напрямую, без хранилища.

## Правила работы с хранилищем

1. Перед захватом — получить актуальную версию. Иначе вы начнёте с устаревшей конфигурации.
2. Захватывать только то, что нужно для задачи, и не держать захват дольше, чем нужно: каждый захват кого-то задерживает.
3. Помещать проверенное. Помещённая ошибка сразу попадает ко всем, кто получит конфигурацию.
4. Писать комментарий как сообщение коммита.
5. Не помещать конфигурацию «целиком на всякий случай»: так в версию попадают чужие объекты и случайные правки.

## Где живёт логика

Хранилище не меняет того, где живёт прикладная логика: правило проведения остаётся в модуле объекта, ограничение — в роли. Меняется путь, которым изменение доходит до коллег.

| Что | Где |
| --- | --- |
| Конфигурация разработчика | его база, подключённая к хранилищу |
| Общая конфигурация и её история | хранилище |
| Кто правит объект сейчас | захват в хранилище |
| Права разработчиков | пользователи хранилища, отдельно от пользователей базы |

## Что важно запомнить

1. Хранилище конфигурации — встроенное в платформу общее место хранения конфигурации и её версий; базы разработчиков к нему подключаются.
2. Цикл работы: получить, захватить, изменить и проверить, поместить с комментарием.
3. Захваченный объект может править только один разработчик; поэтому конфликтов слияния нет, зато бывает ожидание.
4. Новый объект требует захвата корня конфигурации.
5. Отмена захвата возвращает объект в состояние хранилища, правки пропадают.
6. Пользователи хранилища — отдельные учётные записи разработчиков, не пользователи базы.
7. История хранилища отвечает, что, когда, кто и зачем изменил; комментарий пишут как сообщение коммита.
8. Хранилище и Git совмещают: версии хранилища выгружают в Git для истории и ревью.
