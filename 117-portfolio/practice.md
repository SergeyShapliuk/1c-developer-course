# Практика. README проекта и проверка развёртывания

## Перед началом

Понадобятся репозиторий `construction-erp` в ветке `main` после занятия 110, учебная база, совпадающая с `main`, и конспект. Убедитесь: выгрузите конфигурацию и выполните `git status` — изменений нет.

Работаем по процессу этапа 9: изменения портфолио — это доработка проекта, и она идёт через ветку.

```bash
git switch main
git pull
git switch -c docs/portfolio
```

На шаге 6 появится новая информационная база, а конфигурацию учебной базы мы не меняем, поэтому резервная копия сегодня не нужна.

## Шаг 1. Проверьте, что увидит читатель

1. Посмотрите историю так, как её увидит читатель:

```bash
git log --oneline --graph --decorate -25
git tag
```

2. Посмотрите, какие авторы и адреса записаны в истории.

Git Bash:

```bash
git log --format="%an <%ae>" | sort -u
```

PowerShell:

```powershell
git log --format="%an <%ae>" | Sort-Object -Unique
```

3. Запишите в конспект, что вы видите: сколько веток слито коммитами слияния, какие теги есть, какие адреса почты стоят в коммитах. Если там ваш личный адрес, а репозиторий вы собираетесь публиковать, решите сейчас, допустимо ли это. Переписывать уже сделанные коммиты в курсе мы не будем; для новых коммитов адрес можно сменить командой `git config user.email` в этом репозитории.

**Проверка:** в конспекте записаны число слияний, теги и адреса авторов; решение о публикации адреса принято.

## Шаг 2. Напишите README проекта

Создайте в корне `construction-erp` файл `README.md` с разделами из теории. Ниже — что должно быть в каждом; формулировки пишите сами.

1. **Заголовок и одна-две фразы о проекте.** Учебная конфигурация «Управление строительной компанией с логистикой» на платформе «1С:Предприятие 8.3», построенная за курс из 120 занятий. Укажите версию платформы, на которой вы работали.
2. **Возможности.** Восемь-десять пунктов языком пользователя: заявки на материалы и их согласование, поступление на основании заявки, передача на объекты с контролем остатка, запрет передач на завершённые объекты и будущей датой, цены на дату, отчёты для снабжения, печать заявки, накладной и приходного ордера, роли и доступ кладовщика к своему складу, журнал важных событий.
3. **Архитектура.** Таблица из главных объектов: `ЗаявкаНаМатериалы`, `ПоступлениеМатериалов`, `ПередачаМатериалов`, `ЦеныМатериалов`, `ОстаткиМатериалов`, общий модуль `ОстаткиМатериаловСервер`, отчёты, роли, расширение `ДоработкиСнабжения`, обработка `ТестыСнабжения` — по одной строке назначения у каждого.
4. **Развёртывание.** Пронумерованные шаги: создать пустую базу, загрузить конфигурацию из `src/cf`, обновить конфигурацию базы данных, добавить расширение и загрузить его из `src/cfe/ДоработкиСнабжения`, создать пользователя-администратора с ролью `ПолныеПрава`. Отдельно отметьте: пользователи базы не хранятся в выгрузке, их создают после развёртывания.
5. **Тесты.** Как запустить **Разработка → Тесты снабжения**, что проверяют тесты и где лежит регрессионный набор `tests/regression.md`.
6. **Процесс разработки.** Ветки задач, pull request и ревью, слияние коммитом слияния, версии и теги, поставка файлом `.cf`. Здесь же — прямо: второй разработчик в истории, Орлов Дмитрий, — учебная роль, которую играл автор.
7. **Известные ограничения.** Не меньше четырёх пунктов, например: перепроведение поступления с меньшим количеством не контролирует остаток; передача задним числом не контролирует остаток — осознанное решение; пароли учебных пользователей пустые; одновременная отмена поступления и передача того же материала не рассматривались; обработка тестов входит в поставку.

**Проверка:** в `README.md` семь разделов; раздел ограничений содержит не меньше четырёх пунктов; учебная роль Орлова названа.

## Шаг 3. Запишите архитектурные решения

Создайте файл `docs/decisions.md`. Запишите в нём пять-шесть решений по образцу таблицы теории, но своими словами: что выбрали, какие были варианты и почему выбрали именно это. Номер занятия курса, где принималось решение, запишите для себя в конспект, а не в `docs/decisions.md`: читателю репозитория он ничего не скажет.

Хотя бы одно решение выберите сами, не из таблицы теории, — то, которое вам кажется самым интересным в проекте. Его вы будете рассказывать на собеседовании.

**Проверка:** в `docs/decisions.md` пять-шесть решений с вариантами и причинами, одно выбрано вами.

## Шаг 4. Добавьте списки изменений версий

1. Создайте каталог `docs/releases` и скопируйте в него из конспекта списки изменений `1.1.0.md` и `1.2.0.md` (занятия 103 и 110).
2. Сошлитесь на них из README в разделе процесса разработки.

Списки изменений писались для пользователей и администратора рабочей базы — для читателя портфолио они показывают, что вы доводите изменения до поставки.

**Проверка:** в `docs/releases` два списка изменений, README на них ссылается.

## Шаг 5. Прочитайте README глазами чужого человека

1. Откройте `README.md` в любом средстве просмотра Markdown — например, в среде разработки с предпросмотром — и прочитайте его целиком.
2. Ответьте на вопросы читателя из теории, глядя только в README: что это, что умеет, как устроено, как запустить, как проверяется, как велась разработка, что не сделано. Если на какой-то вопрос README не отвечает — допишите.
3. Уберите из README всё, что понятно только вам: номера занятий без пояснения, сокращения, ссылки на конспект.

**Проверка:** на каждый из семи вопросов читателя README отвечает сам, без конспекта и курса.

## Шаг 6. Разверните проект строго по README

Инструкция развёртывания, которую никто не проверял, обычно не работает. Проверим свою.

1. Создайте пустую информационную базу `УСК_Портфолио`.
2. Выполните раздел «Развёртывание» README **дословно** — только то, что там написано, в том порядке, в каком написано.
3. Если какой-то шаг непонятен или не сработал — остановитесь, исправьте README и начните с пункта 1 заново, с новой пустой базой.
4. Когда развёртывание прошло, запустите базу под созданным администратором, откройте **Разработка → Тесты снабжения** и выполните тесты. Все проверки пройдены — тесты создают свои данные и не зависят от данных базы, поэтому работают и в пустой базе.
5. Удалите базу `УСК_Портфолио` из списка и с диска.

**Проверка:** пустая база развёрнута по README без отступлений, тесты в ней пройдены.

## Шаг 7. Закоммитьте и слейте

```bash
git status
git add README.md docs
git commit -m "Add project README, decisions and release notes"
git push -u origin docs/portfolio
git switch main
git merge --no-ff docs/portfolio -m "Merge docs/portfolio: project README for portfolio"
git push
git branch -d docs/portfolio
git push origin --delete docs/portfolio
```

Перед коммитом посмотрите `git status`: в списке только `README.md` и каталог `docs`, конфигурация не менялась.

**Проверка:** README и документы в `main` через коммит слияния, ветка удалена.

## Шаг 8. Опубликуйте репозиторий — по желанию

Эта часть необязательна. Если вы решили публиковать проект и у вас настроен GitHub (занятие 10):

1. Создайте на GitHub пустой **публичный** репозиторий. Если на занятии 103 вы уже создали закрытый репозиторий `construction-erp`, можно сделать его публичным в настройках, а не создавать новый.
2. Отправьте в него `main` и теги:

```bash
git push github main
git push github --tags
```

Если удалённого репозитория `github` у вас нет, сначала добавьте его командой `git remote add github <url>`, как на занятии 103.

3. Откройте страницу репозитория: README показан на главной, теги — в списке версий. Откройте любой файл модуля — например, модуль объекта передачи — и убедитесь, что он читается в браузере.
4. Проверьте ещё раз: в репозитории нет файлов `.dt`, `.cf`, `.cfe` и личных документов.

Клон Орлова и учебный сервер на диске не публикуются: это инструменты курса.

**Проверка:** если репозиторий опубликован, README и теги видны на GitHub, лишних файлов нет; если нет — решение и причина записаны в конспект.

## Шаг 9. Подготовьте рассказ о проекте

Создайте в конспекте файл `career/project-pitch.md` и напишите рассказ о проекте на две минуты:

1. Что это — одна фраза.
2. Что умеет — три-четыре главные возможности.
3. Одно решение, выбранное в шаге 3: задача, варианты, ваш выбор и почему.
4. Как вы проверяли работу: тесты, регрессионный набор, ревью.
5. Что бы сделали дальше — одно-два ограничения из README.

Прочитайте рассказ вслух с таймером. Если он длиннее двух с половиной минут — сокращайте список возможностей, а не решение.

**Проверка:** рассказ записан и укладывается в две с половиной минуты вслух.

## Проверка результата

Занятие пройдено, если выполняются шесть условий:

1. В корне репозитория есть README из семи разделов, отвечающий на вопросы читателя без курса.
2. В README честно описан учебный характер проекта и названы известные ограничения.
3. В `docs` есть архитектурные решения и списки изменений версий.
4. Пустая база развёрнута строго по README, тесты в ней пройдены.
5. Изменения попали в `main` через ветку и коммит слияния.
6. Рассказ о проекте на две минуты записан и проверен вслух.
