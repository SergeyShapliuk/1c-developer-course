# Теория. Когда доработка готова

## Зачем эта контрольная точка

На контрольных точках этапов 3–8 проверялось, умеете ли вы построить механизм: документ, проведение, запрос, отчёт, форму, роль. Здесь проверяется другое — умеете ли вы довести изменение до пользователя так, чтобы оно было понято, проверено, прочитано и поставлено. Код в задаче небольшой. Основная работа — всё, что вокруг кода.

## «Код написан» — не «готово»

Начинающий разработчик говорит «готово», когда код работает в его базе. Для команды это только середина пути. Доработка **готова**, когда выполнены все условия ниже. Многие команды записывают такой список явно и называют его критериями готовности доработки.

| Условие | Где в курсе |
| --- | --- |
| Есть карточка задачи с критериями приёмки, согласованная с заказчиком | 99 |
| Изменение сделано в отдельной ветке понятными коммитами | 100–101 |
| Ветка учитывает свежий `main`, база загружена из файлов ветки | 102 |
| Автоматические тесты пройдены, на исправленную ошибку есть свой тест | 108–109 |
| Регрессионные тест-кейсы пройдены в тестовой базе, есть протокол | 106–107 |
| Есть pull request с описанием, изменения прочитаны по чек-листу ревью | 103–104 |
| Ветка слита в `main`, удалена, база совпадает с `main` | 103 |
| Выпущена версия: номер, тег, поставочный файл из базы, совпадающей с тегом, список изменений | 103 |
| Копия рабочей базы обновлена, критерии приёмки проверены под пользователем | 97, 103 |

## Тест до исправления

В задаче контрольной точки дефект уже известен и описан (занятие 107). Это удобный случай для приёма, который вы видели на занятии 109: **сначала тест, потом исправление**. Тест, написанный до исправления, должен упасть — так вы убеждаетесь, что он ловит именно этот дефект. После исправления тот же тест проходит, и это доказательство, что исправление работает. А дальше тест остаётся в наборе и сторожит, чтобы дефект не вернулся.

## Границы исправления

Отчётов об ошибке на занятии 107 было два: отмена проведения поступления и перепроведение с меньшим количеством. Их причина похожа, но действия пользователя разные. Контрольная задача исправляет первый — вместе с пометкой на удаление, потому что это тот же путь, — а второй остаётся отдельной задачей. Не пытайтесь «заодно» закрыть оба: это ровно то расширение задачи по дороге, от которого предостерегает занятие 99.

## На какие занятия опирается задача

| Что понадобится | Занятия |
| --- | --- |
| Отчёт об ошибке и тест-кейсы | 106–107 |
| Карточка задачи и критерии приёмки | 99 |
| Отмена проведения и движения документа | 44, 47 |
| Проверка остатка после записи движений | 65, 67 |
| Сообщение пользователю с причиной отказа | 24, 48 |
| Тест в транзакции, негативный тест | 108 |
| Ветка, коммиты, слияние, загрузка в базу | 100–102 |
| Pull request, версия, тег, поставка | 103 |
| Чек-лист ревью | 104 |

## Что важно запомнить

1. Доработка готова, когда она понята, проверена, прочитана, слита и поставлена, а не когда код работает у разработчика.
2. Критерии готовности доработки — общий для команды список условий; они повторяют шаги жизненного цикла.
3. Тест на известный дефект пишут до исправления: он должен упасть до и пройти после.
4. Один отчёт об ошибке — одна задача; похожий дефект с другим действием пользователя исправляют отдельно.
