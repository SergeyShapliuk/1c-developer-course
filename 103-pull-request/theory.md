# Теория. От ветки до версии

## Какую задачу мы решаем

Задача «Завершённые объекты» сделана, проверена вами и уже учитывает правило Орлова. Остаются два вопроса.

Первый — кто ещё посмотрит на изменение, прежде чем оно попадёт в `main`. Ошибка, которую вы не заметили сами, через неделю окажется в рабочей базе, и искать её будут уже по жалобе кладовщика.

Второй — как изменение попадёт в рабочую базу. Руководитель спрашивает: «Что именно поставили в пятницу?» Если ответ «то, что было у разработчика в базе», то через месяц повторить или откатить поставку будет невозможно. Нужна версия: известное состояние конфигурации с номером, которое можно найти в истории, собрать заново и описать пользователям.

## Pull request

**Pull request** — запрос на слияние ветки в основную, оформленный на сервере команды. В GitLab тот же механизм называется **merge request**. Pull request объединяет в одном месте три вещи: описание задачи, все изменения ветки и обсуждение этих изменений.

Разработчик открывает pull request, когда считает задачу готовой. **Ревьюер** — другой разработчик — читает изменения, оставляет замечания к конкретным строкам и выносит решение:

| Решение | Что значит |
| --- | --- |
| Одобрение | изменение можно сливать |
| Запрос изменений | есть замечания, которые нужно исправить до слияния |
| Комментарий | вопрос или мнение, не блокирующее слияние |

Исправления по замечаниям делают новыми коммитами в той же ветке: pull request обновляется сам. Сливают ветку, только когда ревьюер одобрил.

Для нашего учебного «сервера» на диске веб-интерфейса нет, и pull request существует как текст в конспекте и как набор команд Git, которые показывают то же, что показал бы GitHub. Механика ревью от этого не меняется.

## Описание pull request

Хорошее описание экономит ревьюеру время и отвечает на вопросы до того, как их зададут. Основа у него та же, что у карточки задачи (занятие 99).

| Раздел | Что в нём |
| --- | --- |
| Задача | ссылка на карточку и одна фраза о проблеме |
| Что сделано | список изменений на уровне объектов конфигурации |
| Как проверить | шаги и ожидаемый результат, по критериям приёмки |
| Что не входит | то, что ревьюер может ожидать, но в задаче нет |
| Поставка и риски | что потребуется при обновлении рабочей базы |

В 1С-проекте раздел «Поставка и риски» особенно важен. Новый реквизит означает реорганизацию таблицы; новая роль — настройку пользователей; изменение расширения — отдельный файл `.cfe`. Администратор, обновляющий рабочую базу, узнает об этом из описания, а не из сообщения платформы посреди обновления.

## Две точки и три точки

Чтобы увидеть то, что видит ревьюер, используют два диапазона.

| Команда | Что показывает |
| --- | --- |
| `git log main..feature/closed-sites` | коммиты ветки, которых нет в `main` |
| `git diff main...feature/closed-sites` | изменения ветки относительно точки, где она ответвилась от `main` |

Три точки в `git diff` важны. Если `main` ушёл вперёд после ответвления, сравнение двумя точками смешало бы изменения ветки с чужими изменениями `main`, показанными «наоборот». Три точки сравнивают ветку с общим предком и показывают только работу по задаче — ровно то, что показывает pull request.

## Слияние в main

После одобрения ветку сливают в `main`. Если ветка уже содержит свежий `main` — как наша после занятия 102, — слияние могло бы пройти перемоткой. Но перемотка растворяет задачу в истории: три коммита задачи выглядят так, будто их сделали прямо в `main`. Ключ `--no-ff` заставляет Git создать коммит слияния даже тогда, когда перемотка возможна. На графе истории задача остаётся отдельной петлёй с понятным сообщением, и её можно откатить одним действием.

Серверы команд предлагают и другие способы — например, **squash**, когда все коммиты ветки склеиваются в один. Какой способ использовать, решает команда; в этом курсе — коммит слияния.

После слияния ветку удаляют — локально и на сервере. Её коммиты остаются в истории `main`, а список веток не зарастает законченными задачами.

## Версия конфигурации

У конфигурации есть свойство **Версия** — строка, которую видит пользователь в окне «О программе» и по которой администратор понимает, что стоит в базе. Обычно версия состоит из трёх или четырёх чисел через точку. В этом курсе их три:

| Часть | Когда растёт | Пример |
| --- | --- | --- |
| Первая | большие изменения, после которых работать придётся по-новому | `2.0.0` |
| Вторая | новые возможности | `1.1.0` |
| Третья | исправления ошибок без новых возможностей | `1.1.1` |

Версию меняют в момент выпуска, отдельным коммитом в `main`, а не в ветке задачи: в одну версию часто входят несколько задач.

## Тег

**Тег** — постоянное имя коммита. В отличие от ветки, тег не двигается: `v1.1.0` через год будет указывать на тот же коммит, что сегодня. Аннотированный тег создают командой `git tag -a v1.1.0 -m "описание"`: у него есть автор, дата и сообщение. На сервер теги отправляют отдельно: `git push origin v1.1.0`.

С тегом вопрос «что поставили в пятницу» получает точный ответ: состояние репозитория под тегом. Из него можно собрать ту же конфигурацию заново, сравнить её со следующей версией или вернуться к ней.

## Поставочный файл и список изменений

Рабочую базу обновляют файлом `.cf` (занятие 97). Его сохраняют из базы, конфигурация которой **совпадает с тегом**: перед сохранением выгружают конфигурацию и убеждаются, что `git status` чист. Файл кладут в хранилище поставок, а не в репозиторий: это результат сборки, а не исходный код.

К версии пишут **список изменений** — короткий текст для пользователей и администратора: что нового, что изменилось в работе, что нужно сделать при обновлении. Его составляют из описаний pull request, вошедших в версию.

## Где живёт логика

| Что | Где | Почему |
| --- | --- | --- |
| Описание изменения для ревьюера | pull request | живёт рядом с изменениями и обсуждением |
| Номер версии | свойство **Версия** конфигурации | его видит пользователь и администратор |
| Точное состояние версии | тег в репозитории | неподвижная ссылка на коммит |
| Поставка | файл `.cf` из базы, совпадающей с тегом | бинарный результат сборки, не исходный код |

## Что важно запомнить

1. Pull request объединяет описание, изменения и обсуждение; ветку сливают только после одобрения ревьюера.
2. Описание pull request отвечает: какая задача, что сделано, как проверить, что не входит, что нужно при поставке.
3. `git log main..ветка` — коммиты ветки; `git diff main...ветка` — её изменения относительно точки ответвления.
4. `--no-ff` сохраняет задачу в истории отдельным коммитом слияния; после слияния ветку удаляют.
5. Версию меняют при выпуске отдельным коммитом в `main`; три числа — большие изменения, новые возможности, исправления.
6. Тег — неподвижное имя коммита; по тегу версию можно собрать заново.
7. Поставочный `.cf` сохраняют из базы, совпадающей с тегом, и хранят вне репозитория; к версии пишут список изменений.
