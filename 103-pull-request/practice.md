# Практика. Версия 1.1.0

## Перед началом

Понадобятся репозиторий `construction-erp` в ветке `feature/closed-sites` после занятия 102, сервер `server/construction-erp.git`, клон Орлова и файл `.dt`, сделанный в начале занятия 100, — снимок учебной базы после этапа 8. Сегодня он сыграет роль рабочей базы компании, которая ещё живёт на версии без доработок этапа 9.

Запустите конфигуратор учебной базы под пользователем «Администратор». Убедитесь, что база совпадает с веткой: выгрузите конфигурацию в `src\cf` и выполните `git status` — изменений быть не должно.

Практика состоит из обязательной части и дополнительной части с GitHub. Дополнительная часть встроена в шаги 3 и 5 и помечена отдельно; без неё занятие считается выполненным.

## Шаг 1. Посмотрите на ветку глазами ревьюера

```bash
git fetch
git log --oneline main..feature/closed-sites
git diff --stat main...feature/closed-sites
git diff main...feature/closed-sites -- src/cf/Documents
```

Первая команда показывает коммиты задачи: три ваших коммита и коммит слияния с `main`. Вторая — список файлов, которые ветка меняет относительно точки ответвления, со счётчиком строк. Третья — сами изменения документа: параметр выбора в `ПередачаМатериалов.xml` и проверку в `ObjectModule.bsl`.

Обратите внимание: проверки Орлова в выводе `git diff main...feature/closed-sites` нет. Она пришла в ветку из `main`, и сравнение с общим предком её не показывает. Ревьюер видит только вашу работу.

**Проверка:** вы видите три файла задачи — справочник, документ, модуль объекта — и ни одного постороннего.

## Шаг 2. Прочитайте изменения сами

Прежде чем звать ревьюера, автор читает свой pull request сам. Выполните полный `git diff main...feature/closed-sites` и пройдите каждую строку со знаком `+` и `-`.

1. Нет ли в изменениях отладочных `Сообщить` и закомментированного кода?
2. Нет ли изменений, которые не относятся к задаче?
3. Совпадает ли то, что вы видите, с разделом «Решение» карточки задачи?

Если что-то нашлось — исправьте в конфигураторе, выгрузите и сделайте ещё один коммит в ветке.

**Проверка:** в изменениях ветки нет ничего, кроме трёх частей решения.

## Шаг 3. Напишите описание pull request

В конспекте создайте файл `pr/closed-sites.md` и напишите описание по разделам теории.

1. **Задача.** Ссылка на `tasks/closed-sites.md` и фраза о проблеме.
2. **Что сделано.** Три изменения: реквизит `Завершен`, параметр выбора у реквизита `ОбъектСтроительства` передачи, проверка в `ОбработкаПроведения`. Отдельной строкой — слияние с `main` и разрешённый конфликт с проверкой будущей даты.
3. **Как проверить.** Пять-шесть шагов из шага 6 занятия 101 с ожидаемым результатом.
4. **Что не входит.** Перенесите раздел «Не входит» из карточки.
5. **Поставка и риски.** Реорганизация таблицы справочника `ОбъектыСтроительства` при обновлении; обновлять, когда в базе нет пользователей; после обновления администратор отмечает сданные объекты.

**Дополнительная часть: pull request на GitHub.** Если у вас есть учётная запись GitHub и настроена авторизация (занятие 10), создайте на GitHub пустой закрытый репозиторий `construction-erp` — без README и `.gitignore` — и отправьте в него обе ветки:

```bash
git remote add github <url>
git push github main
git push github feature/closed-sites
```

Вместо `<url>` подставьте адрес нового репозитория. На странице репозитория откройте pull request из `feature/closed-sites` в `main` и вставьте в описание текст из `pr/closed-sites.md`. Откройте вкладку изменённых файлов и сравните, как читаются изменение модуля и изменение XML. Оставьте у строки проверки в `ObjectModule.bsl` комментарий ревьюера — например, вопрос о тексте сообщения. **Не сливайте pull request на GitHub**: слияние сделаем локально, и GitHub отметит его сам.

**Проверка:** описание pull request в конспекте содержит пять разделов; если вы выполняли дополнительную часть, pull request открыт на GitHub.

## Шаг 4. Слейте задачу в main

Будем считать, что ревьюер одобрил изменения.

```bash
git switch main
git pull
git merge --no-ff feature/closed-sites -m "Merge feature/closed-sites: refuse transfers to completed sites"
git log --oneline --graph -8
git push
```

`git pull` убеждается, что ваш `main` совпадает с сервером. `--no-ff` создаёт коммит слияния, хотя перемотка была бы возможна: ветка уже содержит весь `main`. На графе задача видна отдельной петлёй.

База сейчас загружена из ветки задачи, а `main` после слияния содержит ровно те же файлы. Убедитесь в этом: выгрузите конфигурацию и выполните `git status`. Изменений нет, загружать ничего не нужно.

**Проверка:** в `main` есть коммит слияния `Merge feature/closed-sites: ...`, `main` отправлен на сервер, контрольная выгрузка чиста.

## Шаг 5. Удалите ветку задачи

```bash
git branch -d feature/closed-sites
git push origin --delete feature/closed-sites
git branch -a
```

`git branch -d` удаляет ветку, только если она полностью слита, — защита от потери работы. Вторая команда удаляет ветку на сервере. Коммиты задачи остались в истории `main`.

Ветка Орлова `feature/no-future-transfers` на сервере тоже слита. Удалите её на сервере той же командой `git push origin --delete feature/no-future-transfers`.

**Дополнительная часть.** Отправьте `main` на GitHub командой `git push github main`. Обновите страницу pull request: он отмечен как слитый, хотя вы не нажимали кнопку слияния, — GitHub увидел коммиты ветки в `main`. После этого удалите ветку и там: `git push github --delete feature/closed-sites`.

**Проверка:** `git branch -a` не показывает ни `feature/closed-sites`, ни веток задач на сервере.

## Шаг 6. Отметьте исходную версию тегом

Состояние после этапа 8 — первый коммит репозитория — и есть версия, которая сейчас работает в «рабочей базе». Отметьте его тегом:

```bash
git log --oneline --reverse | head -1
```

PowerShell:

```powershell
git log --oneline --reverse | Select-Object -First 1
```

Команда выводит первый коммит истории. Скопируйте его короткий хеш и создайте тег:

```bash
git tag -a v1.0.0 <хеш> -m "Configuration after stage 8"
```

Вместо `<хеш>` подставьте скопированное значение. Свойство **Версия** в этом коммите не заполнено: так бывает с проектами, которые начинают вести в Git не с первого дня. Тег всё равно фиксирует, что стояло в рабочей базе.

**Проверка:** `git tag` показывает `v1.0.0`, `git show v1.0.0` выводит первый коммит.

## Шаг 7. Выпустите версию 1.1.0

1. В конфигураторе откройте свойства корня конфигурации и задайте **Версия** — `1.1.0`.
2. `Ctrl+S`, `F7`.
3. Выгрузите конфигурацию. `git diff` покажет одну изменённую строку в `Configuration.xml` — номер версии.
4. Закоммитьте, отметьте тегом и отправьте:

```bash
git add src/cf/Configuration.xml
git commit -m "Set configuration version 1.1.0"
git tag -a v1.1.0 -m "Completed construction sites, no future-dated transfers"
git push
git push origin v1.0.0 v1.1.0
git log --oneline --decorate -4
```

Ключ `--decorate` показывает рядом с коммитами имена веток и тегов. Тег `v1.1.0` стоит на коммите версии.

**Проверка:** у конфигурации версия `1.1.0`; теги `v1.0.0` и `v1.1.0` есть локально и на сервере.

## Шаг 8. Соберите поставочный файл

1. Ещё раз выгрузите конфигурацию и убедитесь, что `git status` чист: база совпадает с тегом `v1.1.0`.
2. Выполните **Конфигурация → Сохранить конфигурацию в файл**. Сохраните файл в каталог `releases` рабочего каталога курса — рядом с репозиторием, а не внутри него — под именем `construction-erp-1.1.0.cf`.
3. Расширение `ДоработкиСнабжения` в этой версии не менялось: его поставлять не нужно.

**Проверка:** в каталоге `releases` есть `construction-erp-1.1.0.cf`, `git status` в репозитории чист.

## Шаг 9. Обновите копию рабочей базы

1. В окне запуска создайте новую пустую информационную базу `УСК_Рабочая`.
2. Откройте её в конфигураторе и выполните **Администрирование → Загрузить информационную базу** из файла `.dt` занятия 100. Теперь это копия рабочей базы до доработок этапа 9.
3. Выполните **Конфигурация → Загрузить конфигурацию из файла** и выберите `construction-erp-1.1.0.cf`. Подтвердите замену конфигурации.
4. Выполните `F7`. Прочитайте окно реорганизации: в нём справочник `ОбъектыСтроительства` — тот самый риск из описания pull request. Примите изменения.
5. Запустите `УСК_Рабочая` в режиме **1С:Предприятие** под администратором и откройте **Главное меню → Справка → О программе**. Версия конфигурации — `1.1.0`.
6. Откройте любой объект строительства: у него есть флаг «Завершён», он снят. Отметьте завершённым «ЖК Северный», создайте передачу на него и убедитесь, что она не проводится. Не записывая передачу, закройте её.

Наша конфигурация не стоит на поддержке, поэтому загрузка `.cf` заменяет её целиком. С конфигурацией на поддержке обновление шло бы через сравнение и объединение (занятие 97).

**Проверка:** в `УСК_Рабочая` версия `1.1.0`, флаг «Завершён» работает, реорганизация прошла.

## Шаг 10. Напишите список изменений

В конспекте создайте файл `releases/1.1.0.md` и напишите в нём для пользователей и администратора:

1. **Что нового.** Объект строительства можно отметить завершённым; на завершённый объект нельзя передать материалы, и в новой передаче он не предлагается. Передачу нельзя провести будущей датой.
2. **Что сделать после обновления.** Администратору — отметить сданные объекты.
3. **Особенности обновления.** Реорганизация справочника объектов строительства; обновлять, когда в базе нет пользователей.

Закоммитьте `pr/closed-sites.md` и `releases/1.1.0.md` в конспект.

**Проверка:** список изменений версии `1.1.0` в истории конспекта.

## Проверка результата

Занятие пройдено, если выполняются семь условий:

1. В конспекте есть описание pull request с пятью разделами.
2. `feature/closed-sites` слита в `main` коммитом слияния и удалена локально и на сервере.
3. У конфигурации версия `1.1.0`, изменение версии — отдельный коммит в `main`.
4. Теги `v1.0.0` и `v1.1.0` есть в репозитории и на сервере.
5. Файл `construction-erp-1.1.0.cf` лежит вне репозитория и сохранён из базы, совпадающей с тегом.
6. Копия рабочей базы `УСК_Рабочая` обновлена этим файлом и показывает версию `1.1.0`.
7. В конспекте есть список изменений версии.
