# Теория. Одна задача — одна ветка

## Какую задачу мы решаем

Вы начали задачу «Завершённые объекты»: добавили реквизит, а проверку в проведении ещё не дописали. В этот момент кладовщик сообщает об ошибке в печатной форме накладной, и её нужно исправить сегодня. Если вся работа идёт в `main`, у вас два плохих варианта: отправить исправление вместе с недоделанным реквизитом или отложить исправление до конца задачи.

Ветки, знакомые по занятию 10, решают эту проблему. Каждая задача живёт в своей ветке, `main` содержит только законченные и проверенные изменения, а переключиться на срочное исправление можно в любой момент.

## Ветка под задачу

**Ветка под задачу** — ветка, которую создают от свежего `main` для одной задачи и удаляют после того, как задача слита обратно. Её имя говорит, что в ней делается. Обычно в имени есть вид работы и короткое описание:

| Вид | Пример | Когда |
| --- | --- | --- |
| `feature/` | `feature/closed-sites` | новая возможность |
| `bugfix/` | `bugfix/waybill-total` | исправление ошибки |

В командах к имени часто добавляют номер задачи из системы учёта задач, например `feature/1042-closed-sites`. Правило выбирает команда; важно, чтобы по имени ветки было понятно, к какой задаче она относится.

Одна ветка — одна задача. Если по ходу работы возникла соседняя идея из раздела «Не входит» карточки (занятие 99), для неё заводят отдельную задачу и потом отдельную ветку.

## Атомарный коммит

**Атомарный коммит** — коммит, который делает один логический шаг и после которого конфигурация в рабочем состоянии. Задача «Завершённые объекты» естественно делится на три шага: реквизит, параметр выбора, проверка в проведении. Три коммита — три шага, и каждый можно прочитать, обсудить и при необходимости откатить по отдельности.

Противоположность — коммит «всё за день». В нём перемешаны реквизит, проверка, случайно сдвинутая колонка формы и отладочный `Сообщить`. Прочитать его на ревью тяжело, откатить можно только целиком.

## Сообщение коммита

Сообщение отвечает на вопрос «что делает этот коммит». Первая строка короткая, в повелительной форме, без точки в конце: `Refuse transfers to completed sites`. Если нужно объяснить «почему», после пустой строки пишут подробности.

Язык сообщений выбирает команда. В этом курсе, как и на занятии 10, сообщения написаны по-английски. Русские сообщения тоже нормальны; плохо, когда в одном репозитории их смешивают.

| Плохо | Почему | Лучше |
| --- | --- | --- |
| `fix` | непонятно, что исправлено | `Fix waybill total for multi-page print` |
| `Изменения` | ничего не говорит | `Add completed flag to construction sites` |
| `Add flag, check, choice and fix form` | четыре шага в одном коммите | четыре коммита |

## Что меняет каждое действие

После выгрузки `git status` показывает, какие файлы изменились. Это способ увидеть изменение глазами Git и убедиться, что в коммит попадает ровно то, что задумано.

| Действие в конфигураторе | Что меняется в выгрузке |
| --- | --- |
| Добавить реквизит справочника | файл справочника, например `Catalogs/ОбъектыСтроительства.xml` |
| Изменить свойство реквизита документа | файл документа, например `Documents/ПередачаМатериалов.xml` |
| Изменить код модуля объекта | `Documents/.../Ext/ObjectModule.bsl` |
| Изменить элемент формы | `Forms/.../Ext/Form.xml` |
| Добавить новый объект | его файлы и `Configuration.xml`, где перечислены все объекты |

Если в списке появился файл, которого не ожидали, — это сигнал остановиться. Перед коммитом смотрят `git diff` по каждому неожиданному файлу.

## Случайное изменение

Случайные изменения в конфигураторе бывают постоянно: передвинули элемент формы, поменяли свойство не того реквизита, открыли и сохранили объект, в котором что-то поправили неделю назад. Git заметит их после выгрузки.

Первое желание — отменить изменение в файле командой `git restore`. Она действительно вернёт файл к закоммиченному состоянию. Но **база при этом не изменится**: в конфигурации базы случайная правка осталась, и следующая выгрузка снова принесёт её в файлы.

Поэтому случайное изменение исправляют там, где оно сделано, — в конфигураторе. Затем выгружают ещё раз и убеждаются, что Git больше не видит изменения. Если правок много и вспомнить их нельзя, базу возвращают к состоянию репозитория загрузкой конфигурации из файлов (занятие 100).

`git restore` полезен в обратном случае — когда файл испортили в репозитории, а база правильная. Например, если кто-то открыл файл модуля в редакторе и случайно его изменил.

## База и ветка

У вас одна база разработки и несколько веток. В каждый момент база соответствует одной из них — той, из которой в неё последний раз загружали или в которую из неё выгружали. Переключение ветки командой `git switch` меняет файлы, но не базу.

Отсюда правило для этого этапа: **пока задача не закончена, не переключайте ветку**. На занятии 102 вы увидите, как правильно переключаться: выгрузить и закоммитить своё, переключить ветку, загрузить конфигурацию из файлов, обновить базу.

## Где живёт логика

| Часть задачи | Где | Файл выгрузки |
| --- | --- | --- |
| Признак «Завершён» | реквизит справочника `ОбъектыСтроительства` | `Catalogs/ОбъектыСтроительства.xml` |
| Не предлагать завершённый объект | параметры выбора реквизита `ОбъектСтроительства` документа | `Documents/ПередачаМатериалов.xml` |
| Не проводить передачу на завершённый объект | `ОбработкаПроведения` модуля объекта передачи | `Documents/ПередачаМатериалов/Ext/ObjectModule.bsl` |

## Что важно запомнить

1. Каждая задача — своя ветка от свежего `main`; в `main` попадает только законченное.
2. Имя ветки говорит о виде работы и задаче: `feature/closed-sites`, `bugfix/waybill-total`.
3. Атомарный коммит — один логический шаг, после которого конфигурация работает.
4. Сообщение коммита короткое, в повелительной форме и отвечает, что делает коммит.
5. После выгрузки `git status` и `git diff` показывают, что именно изменилось; неожиданный файл — повод остановиться.
6. `git restore` откатывает файл, но не базу; случайное изменение исправляют в конфигураторе.
7. Переключение ветки меняет файлы, но не базу; база следует за веткой только через загрузку.
