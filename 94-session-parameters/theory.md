# Теория. Текущий пользователь и параметры сеанса

## Какую задачу мы решаем

Петров создаёт передачу и каждый раз выбирает в поле «Ответственный» себя, а в поле «Склад» — свой «Центральный склад». Двадцать передач в день — двадцать одинаковых выборов. Иногда он ошибается и ставит ответственным коллегу, и через месяц уже не понять, кто на самом деле выдал цемент.

База теперь знает, кто вошёл: пользователя «Петров» (занятие 91). Но документы ссылаются не на пользователей, а на элементы справочника `Сотрудники`: ответственный в передаче — сотрудник (занятие 50). Пользователь и сотрудник — разные сущности, и между ними пока нет связи. Нужна связь и место, где один раз за вход вычисляется: «этот пользователь — такой-то сотрудник, его склад — такой-то».

На занятии 95 то же самое понадобится для ограничения доступа: кладовщик должен видеть только передачи своего склада.

## Пользователь и сотрудник

**Пользователь информационной базы** — учётная запись для входа: имя, пароль, роли. Его нельзя выбрать в реквизите документа: пользователи — не данные конфигурации.

**Сотрудник** — элемент справочника: ФИО, должность, телефон. На сотрудника ссылаются документы.

Связь между ними хранят в справочнике сотрудников: реквизит `ИмяПользователя` строкой хранит имя пользователя информационной базы. Не у каждого сотрудника есть пользователь — водитель в базе не работает. Не у каждого пользователя есть сотрудник — у «Администратора» его нет.

Связь по имени — самая простая, но хрупкая: переименовали пользователя — связь потерялась. В рабочих конфигурациях связывают по уникальному идентификатору пользователя, который не меняется при переименовании. Для учебного проекта хватит имени; это стоит записать в технический долг.

Имя текущего пользователя возвращает функция `ИмяПользователя()`.

## Сеанс

**Сеанс** — один вход пользователя в базу: от запуска программы до её закрытия. Внутри сеанса пользователь не меняется. Поэтому вопрос «какой сотрудник сейчас работает» достаточно решить **один раз за сеанс**, а не искать сотрудника по имени при каждом новом документе.

## Параметры сеанса

**Параметр сеанса** — объект конфигурации в ветке **Общие → Параметры сеанса**: значение заданного типа, которое живёт, пока длится сеанс. У каждого сеанса оно своё: у Петрова `ТекущийСотрудник` — «Петров Пётр», у Сидоровой в то же самое время — «Сидорова Анна».

| Параметр сеанса | Тип | Значение |
| --- | --- | --- |
| `ТекущийСотрудник` | `СправочникСсылка.Сотрудники` | сотрудник, связанный с вошедшим пользователем |
| `ТекущийСклад` | `СправочникСсылка.Склады` | склад этого сотрудника |

Обращаются к ним через коллекцию `ПараметрыСеанса`: `ПараметрыСеанса.ТекущийСотрудник`. Параметры сеанса доступны на сервере.

У параметров сеанса есть свои права в ролях: **Получение** — читать значение, **Установка** — менять его. Чтобы код, работающий от имени Петрова, прочитал `ТекущийСотрудник`, роли Петрова нужно **Получение** этого параметра. Для права, которое нужно всем, место — роль `БазовыеПрава`.

Есть у параметров сеанса и вторая роль, ради которой их часто заводят: на них могут опираться **ограничения доступа на уровне записей**. Условие «склад документа равен складу текущего сотрудника» сможет использовать только параметр сеанса — функции в таком условии не вызываются. Этим займётся занятие 95.

## Модуль сеанса

Заполняет параметры сеанса **модуль сеанса** — особый модуль конфигурации, его открывают из контекстного меню корня конфигурации. В нём платформа вызывает обработчик:

```bsl
Процедура УстановкаПараметровСеанса(ИменаПараметровСеанса)

КонецПроцедуры
```

Платформа вызывает его в начале сеанса, а потом — если код обратился к параметру, который ещё не установлен. Параметр `ИменаПараметровСеанса` говорит, какие параметры нужны; в простом случае можно устанавливать все сразу.

Модуль сеанса выполняется на сервере в **привилегированном режиме** (занятие 93): ему не нужны ни **Установка** параметров, ни **Чтение** справочника сотрудников в ролях пользователя. Это и есть узкое служебное действие, для которого привилегированный режим существует: вычислить, кто вошёл, и запомнить.

## Значение по умолчанию в документе

Когда параметры сеанса заполнены, подставить ответственного и склад в новую передачу просто. Вопрос — где.

На занятии 36 мы разобрали обработчик модуля объекта `ОбработкаЗаполнения`. Платформа вызывает его, когда документ **создаётся**: при вводе на основании, при обычной команде **Создать** — тогда `ДанныеЗаполнения` равны `Неопределено` — и при заполнении из кода методом `Заполнить`. Это лучшее место для значений по умолчанию: они подставятся, через какую бы форму или какой бы код документ ни создавался.

Заполнять нужно только пустые реквизиты. Если документ создан на основании и ответственный уже перенесён из основания, затирать его текущим сотрудником нельзя.

## Где живёт логика

| Что | Где | Почему |
| --- | --- | --- |
| Связь пользователя и сотрудника | реквизит `ИмяПользователя` справочника `Сотрудники` | данные, их ведёт администратор |
| Кто вошёл и какой у него склад | параметры сеанса, заполненные модулем сеанса | вычисляется один раз за сеанс, доступно ограничениям доступа |
| Ответственный и склад нового документа | `ОбработкаЗаполнения` модуля объекта | срабатывает при любом создании документа |
| Право читать параметры сеанса | роль `БазовыеПрава` | нужно всем пользователям |

## Что важно запомнить

1. Пользователь — учётная запись для входа, сотрудник — элемент справочника, на который ссылаются документы; связь между ними хранят в справочнике сотрудников.
2. `ИмяПользователя()` возвращает имя текущего пользователя; связь по имени проста, но рвётся при переименовании пользователя.
3. Параметр сеанса — значение, которое живёт один сеанс и у каждого сеанса своё; к нему обращаются через `ПараметрыСеанса`.
4. Модуль сеанса заполняет параметры в обработчике `УстановкаПараметровСеанса` и выполняется в привилегированном режиме.
5. Для чтения параметра сеанса роли нужно право **Получение**.
6. Значения по умолчанию для нового документа подставляют в `ОбработкаЗаполнения` модуля объекта и только в пустые реквизиты.
