# Теория. Как выполнять тестовое задание

## Зачем эта контрольная точка

Многие работодатели перед наймом junior-разработчика дают тестовое задание: «сделайте документ с проведением и проверкой, пришлите результат». По нему видно то, чего не покажет ни экзамен, ни разговор: доводите ли вы работу до конца, читаете ли условие, проверяете ли результат, умеете ли объяснить сделанное.

Итоговая контрольная точка устроена так же. Задача — новая для вас, но каждый её кусок вы уже делали: документ — на этапе 3, проведение — на этапе 4, контроль запросом — на этапе 5, права — на этапе 8, ветки, тесты и поставка — на этапе 9. Проверяется, сможете ли вы собрать их вместе без подсказок.

## Как работают над тестовым заданием

1. **Прочитать условие целиком и задать вопросы.** Неясное место в тестовом задании — не повод угадывать, а повод спросить. Если спросить некого — записать своё решение и его причину в описание результата.
2. **Оценить время до начала** и записывать фактическое. Работодатель спросит, сколько ушло; честное «десять часов вместо восьми, вот где я задержался» лучше, чем неправда.
3. **Сначала сквозной минимум, потом остальное.** Документ, который проводится и меняет остаток, — раньше прав, печати и красоты. Не дописанное к сроку должно быть тем, что менее важно.
4. **Проверять по ходу**, а не в конце: каждый этап заканчивается проверкой, как в контрольных точках курса.
5. **Описать результат.** Что сделано, как проверить, что не сделано и почему, какие решения приняты. Для тестового задания это README или сопроводительное письмо; в курсе — pull request.

## Где спрятана трудность

В задаче есть место, где очевидное решение неверно. Правило «нельзя вернуть больше, чем передано на объект» опирается на передачи **всех** складов. А кладовщик по ограничению доступа (занятие 95) видит только передачи своего склада. Правило учёта не должно зависеть от того, что видит пользователь: иначе кладовщик не сможет вернуть материал, переданный с другого склада, или, наоборот, вернёт больше, чем можно.

Вспомните, что курс говорил о проверках, которые должны видеть больше пользователя (занятие 93), и о запросах к ограниченным данным (занятия 95 и 98). Решение — в одном из этих двух мест, и выбор между ними — главный вопрос задачи.

## На какие занятия опирается задача

| Что понадобится | Занятия |
| --- | --- |
| Карточка задачи, оценка, границы | 99 |
| Документ, реквизиты, табличная часть, форма | 26–31 |
| Проверки документа и сообщения у поля | 33, 48 |
| Ввод на основании | 36 |
| Регистратор, движения, проведение | 44–46, 50 |
| Запрос с временными таблицами, группировкой и соединениями, таблица значений как источник | 58, 59, 63 |
| Права роли, ограничение на уровне записей, привилегированный режим | 92, 93, 95 |
| Параметры сеанса для значений по умолчанию | 94 |
| Ветка, выгрузка, слияние, pull request, версия, поставка | 100–103 |
| Самопроверка по чек-листу ревью | 104 |
| Тест-кейсы, негативные сценарии, автоматические тесты | 106–108 |
| README портфолио | 117 |

## Что важно запомнить

1. Тестовое задание проверяет, доводите ли вы работу до проверенного результата и умеете ли его описать.
2. Неясное в условии спрашивают; если спросить некого — записывают решение и причину.
3. Время оценивают до начала и записывают фактическое.
4. Сначала сквозной минимум, потом остальное; каждый этап заканчивают проверкой.
5. Правило учёта не должно зависеть от того, какие данные видит пользователь.
