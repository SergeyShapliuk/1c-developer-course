# Теория. Конфигурация как исходный код

## Какую задачу мы решаем

Через месяц после запуска прав доступа руководитель снабжения спрашивает: «Правило о срочной заявке появилось до или после того, как Сидорова оформила заявку на щебень? И что именно тогда проверяла программа?» Ответить нечем. В учебной базе есть только текущая конфигурация. Файлы `.dt` из каждого занятия хранят снимки, но чтобы найти в них нужное правило, придётся разворачивать базы по одной и читать модули глазами.

Ещё один вопрос — на будущее. На занятиях 101–110 над конфигурацией будут работать два человека: вы и коллега. Каждый правит свою базу разработки. Как собрать их изменения в одну конфигурацию так, чтобы ничего не потерялось?

Оба вопроса решает то, что вы попробовали на занятии 10: конфигурация, выгруженная в текстовые файлы и хранящаяся в Git. Тогда выгрузка лежала в конспекте и делалась один раз. Теперь у проекта будет собственный репозиторий, и выгрузка станет постоянной частью работы.

## Что в проекте 1С исходный код

**Исходный код конфигурации** — то, из чего конфигурацию можно собрать заново и что имеет смысл сравнивать по версиям. В проекте на платформе это текстовая выгрузка конфигурации и выгрузки её расширений.

| Что | Исходный код? | Почему |
| --- | --- | --- |
| Выгрузка конфигурации в файлы | да | из неё собирается конфигурация, по ней видны построчные изменения |
| Выгрузка расширения в файлы | да | расширение — отдельная конфигурация со своей выгрузкой (занятие 97) |
| Файл `.cf`, файл `.cfe` | нет | бинарная упаковка готового результата, для поставки (занятие 97) |
| Файл `.dt` | нет | данные компании и конфигурация вместе; резервная копия, а не код |
| Каталог файловой базы | нет | рабочие файлы платформы, их не копируют руками |

Отсюда правило: **в репозитории проекта лежит только текстовая выгрузка**. Файлы `.dt`, `.cf` и `.cfe` хранят отдельно — в папке резервных копий или в хранилище поставок.

## Как устроена выгрузка

Команда **Конфигурация → Выгрузить конфигурацию в файлы** раскладывает конфигурацию по каталогам. В **иерархическом формате**, который используют по умолчанию, каждому виду объектов соответствует каталог, а каждому объекту — файл описания и, если нужно, подкаталог.

| Путь в выгрузке | Что внутри |
| --- | --- |
| `Configuration.xml` | свойства самой конфигурации и список всех её объектов |
| `Catalogs/ОбъектыСтроительства.xml` | реквизиты, свойства и формы справочника |
| `Documents/ПередачаМатериалов.xml` | реквизиты, табличные части, свойства документа |
| `Documents/ПередачаМатериалов/Ext/ObjectModule.bsl` | модуль объекта документа |
| `Documents/ПередачаМатериалов/Forms/ФормаДокумента/Ext/Form.xml` | элементы и команды формы |
| `Documents/ПередачаМатериалов/Forms/ФормаДокумента/Ext/Form/Module.bsl` | модуль формы |
| `Roles/Кладовщик/Ext/Rights.xml` | права роли и ограничения доступа |

Два вида файлов ведут себя по-разному. Файлы `.bsl` — обычный текст модулей, тот же, что вы видите в конфигураторе. Их легко читать в истории и, как увидим на занятии 102, можно сливать. Файлы `.xml` описывают метаданные. Читать их можно, но они длинные, и одно действие в конфигураторе меняет в них сразу много строк. Править их руками не нужно: их пишет и читает платформа.

Имена файлов совпадают с именами объектов, а значит написаны кириллицей. Git по умолчанию показывает такие имена кодами вида `\320\224...`. Настройка `core.quotepath false` возвращает читаемые имена.

## Полная выгрузка и выгрузка изменений

При выгрузке платформа кладёт в каталог служебный файл **`ConfigDumpInfo.xml`**. В нём записано, какая версия каждого объекта выгружена. По нему платформа в следующий раз может выгрузить **только изменения** — объекты, которые поменялись с прошлой выгрузки. Это быстро: правка одного документа не перезаписывает тысячи файлов большой конфигурации.

Сам файл меняется при каждой выгрузке во многих местах сразу. В истории он ничего не объясняет и мешает: два разработчика почти наверняка изменят его по-разному, и при слиянии он даст конфликт на ровном месте. Поэтому `ConfigDumpInfo.xml` обычно **не хранят в Git**: он остаётся на диске, чтобы работала выгрузка изменений, но в историю не попадает.

Если выгрузку изменений сделать не удаётся — например, файл потерялся, — делают полную выгрузку в тот же каталог. Результат для Git тот же: Git сравнивает содержимое файлов, и неизменённые файлы останутся неизменёнными.

## Загрузка конфигурации из файлов

Обратная команда — **Конфигурация → Загрузить конфигурацию из файлов**. Она **заменяет** конфигурацию базы содержимым каталога. После неё, как после любого изменения, нужно обновить конфигурацию базы данных.

Загрузка нужна в трёх случаях: собрать конфигурацию в новой базе; получить изменения коллеги (занятие 102); вернуть базе состояние из истории. Во всех трёх помнят одно: всё, что было в конфигурации базы и не выгружено, загрузка сотрёт. Поэтому перед загрузкой делают резервную копию и выгружают свои незакоммиченные изменения.

Проверить, что выгрузка полна, можно только одним способом — собрать из неё конфигурацию в пустой базе и сравнить с исходной. Это и есть сегодняшняя практика.

## База и файлы

Главное, что меняется с этого занятия, — правило работы. Конфигурация теперь существует в двух местах: в базе разработки и в файлах репозитория. Связывают их две команды.

| Когда | Что делать |
| --- | --- |
| Изменили конфигурацию и хотите закоммитить | выгрузить конфигурацию в файлы, затем коммит |
| Получили чужие изменения или переключили ветку | загрузить конфигурацию из файлов, затем `F7` |

Git не знает о базе, а база — о Git. Если выгрузить забыли, коммит не содержит сделанного. Если забыли загрузить, база работает по старой конфигурации, хотя файлы новые.

## Служебные файлы репозитория

**`.gitignore`** вы знаете с занятия 10. В проекте он исключает файлы `.dt`, `.cf`, `.cfe`, служебный `ConfigDumpInfo.xml` и настройки среды разработки.

**`.gitattributes`** — второй служебный файл Git. Он задаёт, как обращаться с файлами определённых видов. Строка `* -text` говорит: ни в одном файле не менять символы конца строки. Git для Windows по умолчанию может переводить концы строк при записи файлов на диск, а платформе нужно ровно то, что она выгрузила. Так загрузка получит из репозитория байт в байт те же файлы.

## Где ещё встретится выгрузка

Конфигуратор — не единственная среда разработки на платформе. В **1С:Enterprise Development Tools** (EDT) проект с самого начала хранится в файлах, и Git встроен в среду. Формат файлов EDT отличается от формата выгрузки конфигуратора, но идея та же: исходный код — текст, а база — место, где этот код запускают. Освоив выгрузку в конфигураторе, вы поймёте и EDT.

## Что важно запомнить

1. Исходный код проекта 1С — текстовая выгрузка конфигурации и расширений; `.dt`, `.cf`, `.cfe` в репозиторий не кладут.
2. В иерархической выгрузке у каждого объекта свой файл описания, модули лежат в файлах `.bsl`, формы — в `Form.xml` и `Module.bsl`.
3. Файлы `.bsl` читают и сливают, файлы `.xml` пишет и читает платформа.
4. `ConfigDumpInfo.xml` нужен для выгрузки изменений и не хранится в Git.
5. Загрузка конфигурации из файлов заменяет конфигурацию базы; перед ней делают `.dt` и выгружают свои изменения.
6. Полноту выгрузки проверяют сборкой конфигурации в пустой базе и сравнением.
7. Правило работы: изменили конфигурацию — выгрузили и закоммитили; получили изменения — загрузили и обновили базу.
8. `core.quotepath false` показывает кириллические имена файлов, `* -text` в `.gitattributes` сохраняет концы строк такими, какими их выгрузила платформа.
