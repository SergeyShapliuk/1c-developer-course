# Практика. Первый репозиторий и выгрузка конфигурации

## Перед началом

Для занятия нужен установленный **Git**. Если его нет, скачайте дистрибутив с официального сайта проекта и установите с настройками по умолчанию — для практики этого достаточно.

Вместе с Git в Windows устанавливается терминал **Git Bash**, и примеры ниже написаны для него. Работать можно и в **PowerShell** — сами команды `git` в обоих терминалах одинаковы. Различаются только вспомогательные команды, которые к Git не относятся: создать файл, удалить файл, обрезать длинный вывод. Там, где такая команда встречается, ниже даны оба варианта — выберите тот, который подходит вашему терминалу. Команды `mkdir` и `cd` работают в обоих терминалах одинаково, поэтому для них вариантов не будет.

Также понадобится информационная база **УправлениеСтроительнойКомпанией** в том состоянии, в котором она осталась после занятия 9.

Практика состоит из двух частей, и они не равнозначны.

**Обязательная часть** — локальный Git. Выполняется целиком на вашем компьютере, интернет не нужен, никакие учётные записи не требуются.

**Дополнительная часть** — GitHub. Она требует учётной записи GitHub и настроенной авторизации. Если авторизация не настроена или учётной записи нет, **занятие считается выполненным после обязательной части**. Пропуск дополнительной части ничего не ломает в курсе: дальше она не понадобится до этапа 9.

## Обязательная часть. Локальный Git

### Шаг 1. Проверьте установку и подпишите свои коммиты

Откройте **Git Bash**. Проверьте, что Git установлен:

```bash
git --version
```

Команда должна вывести номер версии, например `git version 2.45.1`. Если вместо этого вы видите сообщение о неизвестной команде, Git не установлен или не добавлен в системный путь — вернитесь к установке.

Теперь настройте автора. Каждый коммит подписывается именем и адресом электронной почты: это и есть ответ на вопрос «кто это сделал». Без настройки Git откажется создавать коммит.

```bash
git config --global user.name "Иван Иванов"
git config --global user.email "ivan@example.com"
```

Подставьте своё имя и свой адрес. Ключ `--global` означает, что настройка действует для всех ваших репозиториев на этом компьютере. Эти данные попадут в историю каждого коммита и останутся в ней навсегда — поэтому указывайте те, которые не стыдно показать в чужом проекте.

**Проверка:** `git --version` выводит номер версии, имя и почта автора заданы.

### Шаг 2. Создайте репозиторий для конспекта

Перейдите в каталог, где вы держите учебные материалы, и создайте репозиторий.

```bash
mkdir 1c-learning-notes
cd 1c-learning-notes
git init
git status
```

Разберём, что произошло. `mkdir` создал каталог, `cd` перевёл нас в него. `git init` превратил обычную папку в **репозиторий**: внутри появился служебный подкаталог `.git`, где Git хранит всю историю. Править его руками не нужно.

Команда `git status` — самая используемая в Git. Сейчас она сообщает три вещи:

- текущая ветка — `main` (в старых версиях Git она может называться `master`, это нормально);
- коммитов пока нет — история пуста;
- файлов для коммита нет — каталог пуст.

Запомните этот вывод как точку отсчёта.

**Проверка:** `git status` сообщает о ветке без коммитов и отсутствии файлов.

### Шаг 3. Создайте первые файлы

Создайте в каталоге два файла любым текстовым редактором — например «Блокнотом» или редактором вашей среды разработки.

Первый файл — `README.md`. Запишите в него план обучения: заголовок «Конспект обучения 1С», затем раздел «Пройдено» со списком занятий 1–9 и раздел «В работе» со строкой про занятие 10. Содержание произвольное, важно только, чтобы в файле было несколько строк текста: дальше мы будем его менять и смотреть, как Git показывает изменения.

Второй файл — `.gitignore`. Обратите внимание на точку в начале имени: она обязательна, это служебный файл Git. Запишите в него три строки: `*.dt`, `*.cf` и `.idea/` — каждую на отдельной строке.

Разберём каждую строку.

`*.dt` — звёздочка означает «любое имя», поэтому строка исключает все файлы с расширением `.dt`. Это выгрузки информационной базы вместе с данными: бинарные, большие и нечитаемые для Git. Храниться в истории им нечего.

`*.cf` — так же исключает выгрузки конфигурации в бинарном виде. Текстовую выгрузку мы в репозиторий положим, бинарную — нет.

`.idea/` — слеш в конце означает каталог. Это настройки среды разработки конкретного рабочего места: они у каждого свои и другим участникам проекта только мешают.

**Проверка:** в каталоге два файла — `README.md` с планом и `.gitignore` с тремя строками.

### Шаг 4. Сделайте первый коммит

```bash
git add .
git status
git commit -m "Add learning notes"
git log --oneline
```

Что делает каждая команда.

`git add .` добавляет в индекс все изменения текущего каталога — точка означает «всё, что здесь есть». Файлы перешли из рабочего каталога в индекс.

`git status` после этого покажет их в разделе подготовленных к коммиту: файлы **стали подготовленными**. Сравните с выводом из шага 2 — раньше этого раздела не было вовсе.

`git commit -m "Add learning notes"` создаёт коммит из того, что лежит в индексе; ключ `-m` задаёт сообщение прямо в команде. Сообщение пишут коротко и в повелительной форме: оно отвечает на вопрос «зачем это изменение».

`git log --oneline` выводит историю по одной строке на коммит.

**Проверка:** `git log --oneline` показывает один коммит, `git status` сообщает, что изменений нет.

### Шаг 5. Второй коммит и просмотр изменений

Теперь посмотрим, как Git показывает разницу между версиями.

1. Откройте `README.md` и допишите в раздел «В работе» ещё одну строку — например `- Занятие 11. Основы встроенного языка`. Сохраните файл.
2. Выполните команды по очереди, читая вывод каждой:

```bash
git diff
git add README.md
git diff --staged
git commit -m "Update learning plan"
```

`git diff` показывает изменения, которые есть в рабочем каталоге, но ещё не попали в индекс. Видна не «файл изменился», а конкретная добавленная строка со знаком `+` перед ней.

`git add README.md` добавляет в индекс только этот файл. Сравните с шагом 4: там мы добавили всё точкой, здесь — один конкретный файл. Именно так индекс позволяет собрать коммит из нужного.

`git diff --staged` показывает изменения, которые уже лежат в индексе, то есть войдут в следующий коммит. Это последняя возможность проверить состав коммита перед его созданием.

Запомните пару команд: `git diff` — что ещё не подготовлено, `git diff --staged` — что подготовлено.

**Проверка:** `git log --oneline` показывает два коммита, `git status` чист.

### Шаг 6. Поработайте в ветке

```bash
git branch
git switch -c lesson-10
```

`git branch` выводит список ветвей; звёздочкой помечена текущая. Пока ветка одна — `main`.

`git switch -c lesson-10` создаёт ветку `lesson-10` и сразу переключается в неё. Ключ `-c` означает «создать».

Теперь внесите изменение в ветке. Откройте `README.md`, добавьте строку — например `- Git: коммиты и ветки освоены` — и закоммитьте:

```bash
git add README.md
git commit -m "Add git progress note"
git log --oneline
```

История в ветке содержит три коммита. Вернитесь в основную ветку и посмотрите на неё:

```bash
git switch main
git log --oneline
```

В `main` по-прежнему два коммита. Откройте `README.md` в редакторе — строки про Git в нём нет: при переключении ветки Git привёл файлы к состоянию ветки `main`.

Теперь посмотрите всю историю целиком:

```bash
git log --oneline --all
```

Ключ `--all` показывает коммиты всех ветвей, и третий коммит снова виден.

Главный вывод шага: в `main` изменения из ветки не видны, пока их не объединили. Коммит никуда не исчез — он существует, но принадлежит другой линии работы. Поэтому в ветке можно экспериментировать спокойно: основная линия не затронута.

**Проверка:** `git log --oneline` в `main` показывает два коммита, с ключом `--all` — три; файл `README.md` в `main` без строки про Git.

### Шаг 7. Выгрузите конфигурацию в файлы

Переходим из терминала в Конфигуратор.

1. Откройте базу **УправлениеСтроительнойКомпанией** в режиме **Конфигуратор**.
2. Выполните команду **Конфигурация → Выгрузить конфигурацию в файлы**.
3. В окне выбора каталога укажите каталог `src` **внутри** вашего репозитория `1c-learning-notes`. Если такого каталога нет, создайте его в том же окне кнопкой создания папки.
4. Запустите выгрузку и дождитесь её окончания. На нашей небольшой конфигурации это займёт несколько секунд.
5. Откройте каталог `src` в проводнике. Внутри — вложенные каталоги с именами вроде `Catalogs`, `Subsystems`, `DataProcessors`.
6. Откройте один-два файла с расширением `.xml` в «Блокноте» и убедитесь: это обычный текст, который можно читать глазами и сравнивать построчно.

На этом остановитесь. Разбирать формат выгрузки сейчас не нужно — подробностей там много, и к задаче занятия они не относятся. Важно одно: конфигурация представлена текстом, а значит Git покажет по ней построчные изменения.

**Проверка:** в каталоге `1c-learning-notes/src` появились файлы выгрузки, и вы убедились, что они текстовые.

### Шаг 8. Закоммитьте выгрузку и увидьте изменение построчно

Вернитесь в Git Bash. Убедитесь, что вы в каталоге `1c-learning-notes` и в ветке `main`.

```bash
git status
git add src
git commit -m "Add configuration dump"
```

`git status` перед этим покажет каталог `src` как неотслеживаемый. После `git add src` и коммита выгрузка попадает в историю.

Теперь главный опыт занятия. Изменим конфигурацию и посмотрим, что увидит Git.

1. Вернитесь в Конфигуратор.
2. Откройте любой справочник — например `Склады` — и измените его **Синоним** на «Склады материалов».
3. Нажмите `Ctrl+S`, чтобы сохранить конфигурацию. Обновлять базу данных (`F7`) для этой практики не обязательно: нас интересует именно выгрузка.
4. Снова выполните **Конфигурация → Выгрузить конфигурацию в файлы** и укажите **тот же каталог** `src`.
5. Вернитесь в Git Bash и выполните:

```bash
git diff
```

Вы увидите не «файл изменился», а конкретные строки: одна со знаком `−` — старый синоним, другая со знаком `+` — новый. Git показал ровно то, что вы сделали в Конфигураторе.

Вот почему в Git хранят текстовую выгрузку, а не файл `.cf`: по бинарной выгрузке `git diff` сообщил бы только «бинарные файлы различаются», и история не ответила бы, что именно изменилось.

Закоммитьте изменение:

```bash
git add src
git commit -m "Rename catalog synonym"
git log --oneline
```

Если хотите вернуть проект к состоянию занятия 9, верните синоним справочника `Склады` обратно на «Склады», снова выполните выгрузку в каталог `src` и сделайте ещё один коммит с сообщением `Revert catalog synonym`. На результат занятия это не влияет: коммитов станет пять вместо четырёх.

**Проверка:** `git diff` показал изменение синонима построчно, `git log --oneline` содержит не менее четырёх коммитов.

## Дополнительная часть. GitHub

Эта часть **необязательная**. Для неё нужна учётная запись GitHub и настроенная авторизация — по ключу SSH или по токену доступа. Настройка авторизации к теме курса не относится и в разных системах выполняется по-разному. Если авторизация на GitHub не настроена, пропустите эту часть и продолжайте курс: обязательная часть занятия уже выполнена, и никакие последующие занятия на GitHub не опираются.

### Шаг 9. Создайте пустой репозиторий на GitHub

1. Войдите в свою учётную запись на GitHub.
2. Создайте новый репозиторий с именем `1c-learning-notes`.
3. Важно: **не добавляйте README** и не добавляйте `.gitignore` при создании. Репозиторий должен быть пустым. Если GitHub создаст в нём свой первый коммит, ваша локальная история и история на сервере разойдутся, и отправка завершится ошибкой.
4. Скопируйте адрес репозитория, который GitHub покажет после создания.

**Проверка:** на GitHub создан пустой репозиторий, его адрес скопирован.

### Шаг 10. Подключите удалённый репозиторий

```bash
git remote add origin <url>
git remote -v
```

Вместо `<url>` подставьте адрес из шага 9, без угловых скобок.

`git remote add origin` регистрирует удалённый репозиторий под коротким именем `origin`: теперь вместо длинного адреса в командах пишут `origin`. `git remote -v` выводит список удалённых репозиториев с адресами — для проверки, что адрес записан правильно.

**Проверка:** `git remote -v` показывает `origin` с вашим адресом.

### Шаг 11. Отправьте историю на сервер

```bash
git branch -M main
git push -u origin main
```

`git branch -M main` переименовывает текущую ветку в `main`. Если ваша ветка уже называется `main`, команда ничего не изменит — она нужна тем, у кого Git создал ветку с именем `master`.

`git push -u origin main` отправляет коммиты ветки `main` в репозиторий `origin`. Ключ `-u` связывает локальную ветку с одноимённой ветвью на сервере, и в дальнейшем для отправки достаточно будет написать `git push` без параметров.

Git попросит авторизацию, если она не настроена заранее. Если команда завершилась ошибкой доступа — это та самая настройка авторизации, о которой предупреждалось в начале части. Остановитесь здесь: обязательная часть занятия уже выполнена.

**Проверка:** команда завершилась сообщением об отправленных объектах без ошибок.

### Шаг 12. Сравните то, что видно в браузере, с локальной историей

1. Откройте репозиторий в браузере и обновите страницу.
2. Найдите список коммитов. Вы увидите те же сообщения, что и в локальной истории: `Add learning notes`, `Update learning plan`, `Add configuration dump`, `Rename catalog synonym`.
3. Откройте коммит `Rename catalog synonym`. GitHub покажет те же построчные изменения, что показывал `git diff`.
4. Выполните в терминале `git log --oneline` и сравните список с тем, что видите в браузере. Это одна и та же история в двух местах.
5. Сформулируйте своими словами и запишите в конспект: что делает Git, а что делает GitHub.

Ориентир для самопроверки: Git ведёт историю и создаёт коммиты у вас на компьютере, он сделал всю работу обязательной части без интернета. GitHub хранит копию этой истории и показывает её в браузере, чтобы ею было удобно делиться и обсуждать.

**Проверка:** коммиты видны в браузере, и вы записали своими словами разницу между Git и GitHub.

## Проверка результата

Выполните четыре проверки в каталоге `1c-learning-notes`.

1. История содержит не менее четырёх коммитов:

```bash
git log --oneline
```

2. Рабочий каталог чист — незакоммиченных изменений нет:

```bash
git status
```

Ответ должен содержать сообщение о том, что нечего коммитить.

3. Каталог `src` с текстовой выгрузкой конфигурации находится в репозитории и попал в историю:

Git Bash:

```bash
git ls-files src | head
```

PowerShell:

```powershell
git ls-files src | Select-Object -First 10
```

Команда должна вывести несколько путей к файлам выгрузки. Сам `git ls-files src` одинаков везде — отличается только способ показать первые строки длинного вывода.

4. Файлы `.dt` и `.cf` не отслеживаются. Проверим это на деле: создайте тестовый файл и посмотрите, заметит ли его Git.

Git Bash:

```bash
touch test.dt
git status
```

PowerShell:

```powershell
New-Item test.dt -ItemType File
git status
```

Git должен сообщить, что изменений нет: файл `test.dt` он игнорирует согласно правилу `*.dt` из `.gitignore`. Если файл всё же появился в списке неотслеживаемых — проверьте имя и содержимое `.gitignore`.

Удалите тестовый файл.

Git Bash:

```bash
rm test.dt
```

PowerShell:

```powershell
Remove-Item test.dt
```
