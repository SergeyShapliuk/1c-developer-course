# Теория. Контроль версий для 1С-разработчика

## Зачем контроль версий

Ситуация знакома любому, кто что-то разрабатывал. Вчера всё работало. Сегодня не работает. Что именно изменилось за это время — непонятно: правок было десяток, и какая из них всё испортила, уже не вспомнить.

Без истории изменений выход один — вспоминать и перебирать варианты. С историей выход другой: посмотреть, что менялось, найти шаг, после которого поведение изменилось, и откатиться.

**Контроль версий** — это инструмент, который хранит историю изменений файлов и позволяет вернуться к любому сохранённому состоянию. Он отвечает на четыре вопроса: что изменилось, когда, кто это сделал и зачем. Последний вопрос — не формальность: разработчик сам оставляет пояснение к каждому сохранённому состоянию.

Самый популярный инструмент контроля версий — **Git**. Его и разбираем.

## Рабочий каталог, индекс, коммит

У Git три области, и порядок работы всегда идёт через них по очереди. Это главная схема занятия.

**Рабочий каталог** — обычная папка с файлами, которые вы правите. Открыли файл, добавили строку, сохранили — изменение живёт в рабочем каталоге и больше нигде.

**Индекс** (его ещё называют областью подготовленных изменений) — список изменений, отобранных для следующего сохранения. Изменение попадает сюда командой `git add`.

**Коммит** — зафиксированный снимок состояния. У коммита есть автор, дата и сообщение, которое вы написали. Коммит создаётся из того, что лежит в индексе, и после создания больше не меняется.

Зачем нужен индекс между рабочим каталогом и коммитом? Казалось бы, проще было бы коммитить всё сразу. Индекс существует именно для того, чтобы можно было **закоммитить часть изменений, а не всё**.

Пример. За час работы вы исправили ошибку в одном месте и начали переделывать другое, пока недоделанное. Исправление ошибки готово и должно попасть в историю отдельным, понятным коммитом. Недоделанная переделка — нет. Если бы индекса не было, пришлось бы либо коммитить всё в одну кучу, либо ждать, пока будет готово и второе. Индекс позволяет собрать коммит из нужных файлов и оставить остальное на потом.

Второе применение индекса — просмотр. Перед коммитом можно сравнить, что именно вы собрались сохранить, и убедиться, что лишнего там нет.

## Ветка

**Ветка** — отдельная линия работы в истории. Основная ветка по традиции называется `main`.

Смысл ветки в изоляции. Вы создаёте ветку, работаете в ней, делаете коммиты — и основная линия всё это время остаётся нетронутой. Если эксперимент получился, изменения из ветки объединяют с основной линией. Если не получился, ветку просто удаляют, и в `main` ничего не меняется.

Для разработчика это означает свободу экспериментировать. Можно попробовать рискованное решение, не опасаясь испортить работающий код: откат — это не героические усилия, а одна команда.

Переключение между ветками меняет содержимое рабочего каталога: Git приводит файлы в то состояние, которое соответствует выбранной ветке.

## Удалённый репозиторий

**Удалённый репозиторий** — копия истории на сервере. У неё две задачи.

Первая — командная работа. Через удалённый репозиторий несколько человек обмениваются изменениями: каждый отправляет туда свои коммиты и забирает чужие.

Вторая — резервная копия. История на сервере не зависит от вашего ноутбука. Если диск откажет, работа не пропадёт.

Удалённый репозиторий, с которым работают по умолчанию, принято называть `origin`. Отправка изменений туда называется `push`, получение — `pull`.

## Git и GitHub — не одно и то же

Их путают постоянно, и путаница мешает понять, что происходит.

**Git** — программа, установленная на вашем компьютере. Она создаёт репозиторий, ведёт историю, делает коммиты и ветки. Для всего этого **интернет не нужен**: Git полностью работоспособен без сети и без каких-либо сервисов.

**GitHub** — сервис в интернете, на котором можно разместить копию репозитория. Он добавляет к Git удобства для совместной работы: веб-интерфейс, обсуждение изменений, pull request, задачи, права доступа.

Вывод простой: Git без GitHub — полностью рабочий инструмент. Вся обязательная часть практики этого занятия выполняется без интернета. GitHub же без Git бессмысленен: он хранит именно git-репозитории.

Кроме GitHub есть GitLab, Bitbucket и другие похожие сервисы. Git с ними работает одинаково — команды те же.

## Что версионируют в 1С

Здесь у 1С есть своя особенность, которую нужно понять.

Конфигурация внутри информационной базы хранится не в виде обычных файлов на диске, а внутри базы. Выгрузить её целиком можно в файл `.cf`, а всю базу вместе с данными — в файл `.dt`. Оба формата **бинарные**: это один большой файл, который человек не может прочитать в текстовом редакторе.

Git такой файл сохранит, тут проблемы нет. Проблема в другом: Git **не покажет, какая строка изменилась**. Для бинарного файла он может сказать только «файл изменился» и сохранить его целиком, новой копией. История из таких коммитов бесполезна: по ней невозможно увидеть, что именно сделал разработчик.

Поэтому платформа умеет сохранять конфигурацию иначе — как набор текстовых файлов. Это делает команда **Конфигурация → Выгрузить конфигурацию в файлы**. Вы указываете каталог, и платформа раскладывает в него конфигурацию: отдельные файлы с описанием справочников, их реквизитов, форм, модулей.

Именно текстовое представление удобно хранить и сравнивать в Git. Изменили длину наименования справочника — в истории видно ровно одну изменившуюся строку. Поправили синоним — видно, какой был и какой стал. Дописали процедуру в модуль — видно добавленные строки кода.

Разбираться в структуре выгрузки сейчас не нужно: файлов там много, и в них много технических подробностей. Задача занятия другая — увидеть своими глазами, что текстовое представление даёт читаемую историю, а бинарный файл нет.

## .gitignore

**`.gitignore`** — текстовый файл со списком того, что не нужно хранить в истории. Он лежит в репозитории, и Git читает его автоматически.

Что в него обычно попадает:

- бинарные выгрузки `.dt` и `.cf` — они большие, и история по ним нечитаема;
- временные и служебные файлы, которые создаёт среда разработки;
- настройки конкретного рабочего места — они у каждого свои и другим мешают.

Правило простое: в репозитории хранят то, что нужно для работы над проектом и что имеет смысл сравнивать по версиям. Всё остальное — в `.gitignore`.

## Зачем это junior-разработчику

Контроль версий не относится к платформе 1С, но относится к работе 1С-разработчика напрямую.

Любая команда разработки ведёт работу в Git. Вас попросят создать ветку под задачу, сделать коммиты с понятными сообщениями и оформить pull request на проверку. Если вы этого не умеете, в работу вас не включат — независимо от знания платформы.

На собеседовании про Git спрашивают почти всегда, и вопросы ровно базовые: чем коммит отличается от ветки, что делает `git add`, как посмотреть изменения, что такое pull request. Разобравшись в этом один раз, вы закрываете целый блок вопросов.

Командная работа в Git — ветки под задачи, pull request, разрешение конфликтов, разбор чужого кода — разбирается на этапе 9 курса. Сегодняшняя задача скромнее: научиться работать с Git самостоятельно, со своим репозиторием.

## Что важно запомнить

1. Контроль версий хранит историю изменений и позволяет вернуться к любому сохранённому состоянию; он отвечает, что изменилось, когда, кто и зачем.
2. Изменение проходит три области: рабочий каталог → индекс → коммит.
3. Индекс нужен, чтобы закоммитить часть изменений, а не всё сразу, и чтобы проверить состав коммита перед его созданием.
4. Ветка — отдельная линия работы; `main` основная, а в ветке можно экспериментировать, не трогая основную линию.
5. Удалённый репозиторий даёт командную работу и резервную копию истории.
6. Git — программа на вашем компьютере и работает без интернета; GitHub — сервис, где лежит копия репозитория. Git без GitHub полностью рабочий.
7. В Git версионируют текстовую выгрузку конфигурации, потому что по ней видно построчные изменения; `.dt` и `.cf` бинарны и такой истории не дают.
8. `.gitignore` перечисляет то, что не попадает в историю: бинарные выгрузки, временные файлы, личные настройки.
