# Практика. Регрессионный набор снабжения

## Перед началом

Понадобятся учебная база, совпадающая с `main` репозитория `construction-erp` после занятия 104, и конспект `1c-learning-notes`.

1. Запустите конфигуратор учебной базы под пользователем «Администратор» и выгрузите её в новый файл `.dt`.
2. В окне запуска создайте пустую информационную базу `УСК_Тест` и загрузите в неё этот `.dt`: **Администрирование → Загрузить информационную базу**.

Все действия занятия выполняются в `УСК_Тест` под администратором. Учебная база не меняется. Базу `УСК_Тест` не удаляйте: она понадобится на занятии 107.

В конспекте создайте файл `tests/supply-regression.md` — в нём будут тест-кейсы и протокол.

## Шаг 1. Подготовьте набор тестовых данных

В `УСК_Тест` в режиме **1С:Предприятие** создайте:

| Справочник | Элемент | Реквизиты |
| --- | --- | --- |
| Склады | «Склад испытаний» | адрес — любой |
| Товары | «Доска обрезная» | единица измерения `м3` |
| Объекты строительства | «ЖК Пробный» | заказчик — любой, флаг «Завершён» снят |

Откройте отчёт «Остатки на складах» с отбором по «Складу испытаний». Отчёт пуст: на складе ещё не было ни одного документа. Это и есть исходное состояние набора — остаток доски `0`.

В начале файла `tests/supply-regression.md` опишите набор данных: три элемента и исходный остаток.

**Проверка:** три тестовых элемента созданы, отчёт по «Складу испытаний» пуст, набор описан в конспекте.

## Шаг 2. Рассчитайте ожидаемые остатки

Сценарий из десяти тест-кейсов ниже уже записан, но колонка «Ожидаемый остаток» пуста. **Не открывая базу**, рассчитайте и впишите ожидаемый остаток доски на «Складе испытаний» после каждого тест-кейса. Перенесите таблицу в конспект вместе с вашими числами.

| ID | Название | Шаги | Ожидаемый результат | Ожидаемый остаток |
| --- | --- | --- | --- | --- |
| ТК-01 | Поступление даёт приход | провести поступление доски `100` от «ООО СтройСнаб» на «Склад испытаний» | документ проведён; в регистре приход `100` | |
| ТК-02 | Передача даёт расход | провести передачу доски `30` со «Склада испытаний» на «ЖК Пробный» | документ проведён; в регистре расход `30` | |
| ТК-03 | Остаток на дату | сформировать «Остатки на складах» на вчерашнюю дату | строки доски нет | остаток на сегодня не меняется |
| ТК-04 | Отмена проведения передачи | отменить проведение передачи ТК-02 | расхода `30` в регистре нет | |
| ТК-05 | Перепроведение с другим количеством | в передаче ТК-02 поставить `45` и провести | в регистре один расход `45`, не два | |
| ТК-06 | Выдача по объекту | сформировать «Выдача по объектам» | у «ЖК Пробного» доска `45` | |
| ТК-07 | Завершённый объект не принимает передачу | отметить «ЖК Пробный» завершённым; создать передачу доски `5` на «ЖК Пробный» копированием передачи ТК-05, записать без проведения, затем провести | запись прошла, проведение отклонено, сообщение у поля «Объект строительства» | |
| ТК-08 | Завершённый объект не предлагается | создать новую передачу и открыть выбор объекта строительства | «ЖК Пробного» в списке нет | |
| ТК-09 | Проведённая передача остаётся | открыть журнал передач | передача ТК-05 на завершённый «ЖК Пробный» по-прежнему проведена | |
| ТК-10 | Снятие отметки | снять флаг «Завершён» у «ЖК Пробного»; провести передачу ТК-07 | документ проведён; в регистре расход `5` | |

Для ТК-03, ТК-06, ТК-08 и ТК-09 остаток не меняется — впишите, каким он остаётся.

**Проверка:** в конспекте десять ожидаемых остатков, рассчитанных до прогона. Сверьте с ориентиром: после ТК-01 — `100`, после ТК-10 — `50`. Если ваши числа на этих двух шагах другие, пересчитайте, не открывая базу.

## Шаг 3. Прогоните сценарий

Выполняйте тест-кейсы строго по порядку. После каждого:

1. откройте «Остатки на складах» с отбором по «Складу испытаний» и сравните остаток с ожидаемым;
2. если в ожидаемом результате упомянут регистр, откройте форму списка регистра `ОстаткиМатериалов` и найдите записи документа;
3. впишите в конспект фактический результат и статус: «пройден», «не пройден» или «заблокирован».

Если тест-кейс не прошёл, **не исправляйте конфигурацию и не подгоняйте данные**. Запишите фактический результат как есть и решите, можно ли продолжать: если предусловие следующего тест-кейса не выполнено, следующий получает статус «заблокирован».

Пример строки протокола:

| ID | Фактический результат | Фактический остаток | Статус |
| --- | --- | --- | --- |
| ТК-01 | проведено, приход `100` в регистре | `100` | пройден |

**Проверка:** для каждого из десяти тест-кейсов записаны фактический результат и статус.

## Шаг 4. Заполните шапку протокола

Над таблицей результатов запишите:

1. Версия конфигурации — из **Главное меню → Справка → О программе**. В `УСК_Тест` она `1.1.0`, хотя конфигурация взята из `main` и уже содержит подсказку остатков: версию выпускают позже. Запишите оба факта: номер версии и последний коммит `main`, который выводит `git log --oneline -1 main` в репозитории `construction-erp`.
2. База — `УСК_Тест`, восстановлена из `.dt` такого-то числа.
3. Дата прогона и исполнитель.
4. Итог: сколько тест-кейсов пройдено, не пройдено, заблокировано.

**Проверка:** у протокола есть версия, коммит, база, дата, исполнитель и итог.

## Шаг 5. Выберите регрессионный набор

1. Отметьте в конспекте, какие тест-кейсы войдут в регрессионный набор — их будут повторять при каждой новой версии. Обоснуйте каждый выбор одной фразой: что сломается для бизнеса, если этот тест не повторить.
2. Отметьте, какие тест-кейсы проверяют задачу «Завершённые объекты». После её приёмки они становятся частью регрессии.
3. Допишите в набор тест-кейс, который проверял бы подсказку остатков из занятия 104: шаги, ожидаемый результат в числах для «Склада испытаний».

**Проверка:** регрессионный набор выбран и обоснован, в нём есть тест-кейс на подсказку остатков.

## Шаг 6. Сохраните тест-кейсы рядом с проектом

Тест-кейсы относятся к проекту, а не к вашему конспекту: их будет повторять любой, кто выпускает версию. Скопируйте таблицу тест-кейсов — без протокола прогона — в репозиторий проекта:

1. Создайте в `construction-erp` каталог `tests` и файл `tests/regression.md` с описанием набора данных и тест-кейсами.
2. Закоммитьте его в ветке `main`:

```bash
git add tests/regression.md
git commit -m "Add supply regression test cases"
git push
```

Протокол прогона остаётся в конспекте: это запись одной проверки, а не часть проекта. В команде изменения тест-кейсов тоже проходят через pull request; здесь файл новый и не затрагивает конфигурацию, поэтому для краткости он коммитится прямо в `main`.

**Проверка:** в `main` проекта есть `tests/regression.md`, протокол прогона — в конспекте.

## Проверка результата

Занятие пройдено, если выполняются шесть условий:

1. В `УСК_Тест` есть набор тестовых данных, на котором до сценария не было документов.
2. Для десяти тест-кейсов ожидаемые остатки рассчитаны и записаны до прогона.
3. Для каждого тест-кейса записаны фактический результат и статус; несовпадения не исправлены подгонкой.
4. У протокола есть версия, коммит, база, дата, исполнитель и итог.
5. Регрессионный набор выбран, обоснован и дополнен тест-кейсом на подсказку остатков.
6. Тест-кейсы лежат в репозитории проекта, протокол — в конспекте.

## Контрольные вопросы

Не подглядывая в теорию, ответьте устно или в заметках:

1. Из каких частей состоит тест-кейс на учётную логику и чем он отличается от тест-кейса занятия 25?
2. Почему ожидаемый результат записывают до прогона?
3. Зачем свой набор тестовых данных, если в базе уже есть склады и материалы?
4. Что такое регрессия и по какому принципу тест-кейсы попадают в регрессионный набор?
5. Если отчёт «Остатки на складах» показывает `55`, а в регистре движения дают `50`, где искать ошибку?
6. ТК-07 проверяет правило, которое живёт в `ОбработкаПроведения` передачи, а ТК-08 — правило в параметрах выбора её реквизита. Какой из них проверяет гарантию, какой — удобство, и почему при регрессии важнее не потерять ТК-07?

Сверьте ответы с [теорией](theory.md). Если на каждый вопрос получается ответить одним-двумя предложениями, переходите к занятию 107.
