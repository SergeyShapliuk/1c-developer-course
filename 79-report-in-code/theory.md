# Теория. Отчёт из кода

## Какую задачу мы решаем

Десять занятий этапа отчёты обходились без кода: запрос жил в наборе данных, раскладка — в настройках, правила оформления — там же. Это правильно, и так должно оставаться, пока схема справляется. Но у пользователей появились две просьбы, которые схема выполнить не может.

**Кладовщик оформляет передачу.** Перед проведением он хочет одним нажатием увидеть остатки склада этой передачи — не открывать раздел, не искать отчёт, не выбирать склад вручную. Схема отчёта ничего не знает о форме документа, из которой её позвали.

**Бухгалтер открывает оборотную ведомость** и нажимает **Сформировать**, сняв флажок периода, — или выбирает произвольный период и по ошибке ставит начало на два года раньше. Ведомость строится за всю историю склада: долго, бесполезно, и пользователь не понимает, почему ждёт.

Часть второй просьбы схема решает сама. У параметра есть **значение по умолчанию** (занятие 72): если задать параметру `ПериодОтчета` значение «Этот месяц», ведомость открывается сразу за текущий месяц, и кода для этого не нужно. Но флажок периода пользователь может снять, а период — растянуть на годы. Правило «период обязателен и не длиннее года, а иначе — не строить и объяснить почему» схема выразить не может: она не умеет ни отказаться формировать отчёт, ни сказать пользователю, что не так.

Обе задачи требуют кода. Вопрос этого занятия — какого и где.

## Открытие отчёта с отбором

Форма отчёта, как любая форма, открывается методом `ОткрытьФорму` — он доступен только на клиенте (занятие 22). Вторым параметром ему передают **параметры формы** — структуру значений, которые форма учтёт при открытии. У формы отчёта есть стандартные параметры, которые понимает система компоновки:

| Параметр | Что делает |
| --- | --- |
| `Отбор` | структура «имя поля — значение»: отчёт откроется с таким отбором |
| `СформироватьПриОткрытии` | `Истина` — отчёт сформируется сразу, без нажатия **Сформировать** |
| `КлючВарианта` | имя варианта отчёта, который нужно открыть |

```bsl
ПараметрыФормы = Новый Структура;
ПараметрыФормы.Вставить("Отбор", Новый Структура("Склад", Объект.Склад));
ПараметрыФормы.Вставить("СформироватьПриОткрытии", Истина);
ОткрытьФорму("Отчет.ОстаткиНаСкладах.Форма", ПараметрыФормы, ЭтаФорма);
```

Имя формы `Отчет.ОстаткиНаСкладах.Форма` означает «основная форма отчёта». Своей формы у отчёта нет — платформа откроет ту, что строит сама.

Обратите внимание, что этот код не обращается к базе: склад уже есть в данных формы, `Объект.Склад`, и серверный вызов не нужен. Запрос выполнит сам отчёт — на сервере, когда начнёт формироваться.

Отбор, переданный параметром, действует только в этом открытии. Сохранённые настройки кладовщика, например его привычный склад, не меняются.

## Из чего состоит компоновка

Пока модуль отчёта пуст, нажатие **Сформировать** запускает **стандартную обработку**: платформа сама берёт схему и настройки и строит результат. Чтобы решить, где вмешаться в этот процесс, нужно знать его шаги.

```text
Схема компоновки данных       Настройки: вариант + выбор пользователя
         │                                │
         └───────────────┬────────────────┘
                         ▼
        КомпоновщикМакетаКомпоновкиДанных.Выполнить
                         │  какие запросы, какие группировки, какие поля
                         ▼
               Макет компоновки данных
                         │
                         ▼
     ПроцессорКомпоновкиДанных: выполняет запросы наборов,
     связывает наборы, считает ресурсы и группировки
                         │
                         ▼
     ПроцессорВыводаРезультатаКомпоновкиДанныхВТабличныйДокумент
                         │
                         ▼
           Результат в форме отчёта
```

1. **Компоновщик макета** — объект `КомпоновщикМакетаКомпоновкиДанных`. Он получает схему и настройки и решает, *что* нужно сделать: какие запросы выполнить, с какими параметрами, какие поля и группировки построить. Результат его работы — **макет компоновки данных**, план выполнения отчёта.
2. **Процессор компоновки** — объект `ПроцессорКомпоновкиДанных`. Он исполняет план: выполняет запросы наборов, применяет связи, считает ресурсы по группировкам.
3. **Процессор вывода** — объект `ПроцессорВыводаРезультатаКомпоновкиДанныхВТабличныйДокумент`. Он превращает посчитанный результат в лист, который видит пользователь.

Слово «макет» здесь означает план компоновки, а не печатный бланк: макеты печатных форм — тема этапа 7.

Всю эту цепочку при стандартной обработке выполняет платформа. Код может пройти её сам — и тогда должен повторить каждый шаг. Это нужно, когда код меняет настройки перед построением отчёта; в учебном проекте такой задачи нет. Для проверки периода цепочку повторять не нужно: код либо разрешает платформе построить отчёт, либо отказывает.

## ПриКомпоновкеРезультата

У объекта отчёта есть событие **`ПриКомпоновкеРезультата`**. Его обработчик пишут в **модуле отчёта**, и он выполняется на сервере каждый раз, когда пользователь нажимает **Сформировать**, — до того, как платформа начнёт стандартную обработку. Параметры обработчика:

- `ДокументРезультат` — лист, на который выводится результат;
- `ДанныеРасшифровки` — сведения, по которым работает расшифровка двойным щелчком;
- `СтандартнаяОбработка` — если установить `Ложь`, платформа не будет строить отчёт сама.

Внутри модуля отчёта доступны его свойства: `СхемаКомпоновкиДанных` — основная схема и `КомпоновщикНастроек` — настройки, с которыми работает форма. Метод `КомпоновщикНастроек.ПолучитьНастройки()` возвращает **копию** итоговых настроек: вариант вместе с выбором пользователя. По ней код узнаёт, что именно пользователь выбрал.

Значение параметра в настройках находят по его имени:

```bsl
ЗначениеПериода = Настройки.ПараметрыДанных.НайтиЗначениеПараметра(
	Новый ПараметрКомпоновкиДанных("ПериодОтчета"));
```

У найденного значения два свойства: `Использование` — отмечен ли флажок, и `Значение` — само значение. Для параметра типа `СтандартныйПериод` у значения есть `ДатаНачала` и `ДатаОкончания`, как в выражениях занятия 75.

## Отказать, но не перехватить

`СтандартнаяОбработка = Ложь` отменяет стандартную обработку полностью. Если поставить её всегда, платформа не построит отчёт ни разу, и всё, что она делала, придётся делать коду — всю цепочку компоновки. Забыть шаг легко, а пользователь потеряет возможности, которыми уже пользовался: например, если не передать `ДанныеРасшифровки` компоновщику макета и процессору компоновки, двойной щелчок по документу перестанет работать.

Поэтому правило проверки устроено так:

- **период правильный** — обработчик ничего не трогает, `СтандартнаяОбработка` остаётся `Истина`, и отчёт строит платформа, со всеми своими возможностями, включая расшифровку;
- **период неправильный** — обработчик ставит `СтандартнаяОбработка = Ложь`, очищает `ДокументРезультат`, чтобы на листе не остался прошлый результат рядом с сообщением об ошибке, и сообщает пользователю, что исправить.

Код вмешивается только тогда, когда отчёт строить нельзя.

## Где живёт код отчёта

| Задача | Где решается | Почему |
| --- | --- | --- |
| Период по умолчанию — текущий месяц | значение параметра в схеме | схема это умеет, код не нужен |
| Открыть отчёт с отбором из документа | модуль формы документа, `&НаКлиенте` | открытие формы — действие клиента; данные склада уже в форме |
| Проверка периода с сообщением | модуль отчёта, `ПриКомпоновкеРезультата` | выполняется при любом способе формирования, на сервере |
| Получение данных | набор данных схемы | как и раньше — не в коде |

Проверку периода можно было бы попытаться написать в форме отчёта: перед формированием посмотреть на период. Но своей формы у отчёта нет, а если её создать — правило сработает только в ней. Модуль отчёта выполняется при любом формировании отчёта. Это та же логика, что проведение в модуле объекта на занятии 45: правило объекта живёт в объекте, а не в одной из его форм.

И последнее: код в отчёте **не заменяет** схему. В `ПриКомпоновкеРезультата` нет ни запроса, ни вывода строк руками: он только проверяет настройки. Если код в отчёте начинает сам выбирать данные, отчёт превращается обратно в обработку с таблицей — от чего уходили на занятии 69.

## Что важно запомнить

1. Код нужен отчёту, только когда схема не может выразить задачу: связь с местом вызова или проверка настроек с сообщением пользователю. Значение по умолчанию задают в схеме, а не кодом.
2. `ОткрытьФорму` открывает отчёт на клиенте; параметры `Отбор`, `СформироватьПриОткрытии` и `КлючВарианта` задают отбор, немедленное формирование и вариант, не меняя сохранённых настроек.
3. Компоновка — это цепочка: компоновщик макета строит план, процессор компоновки его исполняет, процессор вывода выводит результат. При стандартной обработке её выполняет платформа.
4. `ПриКомпоновкеРезультата` выполняется на сервере в модуле отчёта при каждом формировании; `КомпоновщикНастроек.ПолучитьНастройки()` показывает, что выбрал пользователь.
5. `СтандартнаяОбработка = Ложь` ставят только при отказе: тогда очищают результат и сообщают причину. Если отчёт строить можно, его строит платформа — с расшифровкой.
6. Код в отчёте проверяет настройки, но не выбирает данные сам.
