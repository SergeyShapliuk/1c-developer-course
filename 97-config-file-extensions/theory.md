# Теория. Файл конфигурации и расширения

## Какую задачу мы решаем

До сих пор разработчик и пользователи работали в одной учебной базе: правка в конфигураторе — и через минуту она у пользователей. В компании так не делают. Разработчик дорабатывает **базу разработки** — копию с тестовыми данными. Сотрудники работают в **рабочей базе** с настоящими заявками и остатками. Править рабочую базу напрямую — значит проверять доработку на живых данных и останавливать работу склада при каждой ошибке.

Значит, нужен способ перенести готовую доработку из базы разработки в рабочую, не затронув её данные. И второй вопрос: что делать, если конфигурацию рабочей базы разрабатывает не компания, а поставщик типового решения, и каждые несколько месяцев выпускает обновления?

Руководитель снабжения просит небольшую доработку: срочную заявку нельзя записать без комментария, объясняющего срочность. На этом примере разберём оба способа доставки.

## Файл конфигурации

**Файл конфигурации** с расширением `.cf` хранит конфигурацию — все объекты, формы, модули, роли, макеты — и ничего больше. В нём нет ни данных, ни пользователей. Этим он отличается от файла `.dt` занятия 91, который хранит базу целиком.

| Файл | Что внутри | Для чего |
| --- | --- | --- |
| `.dt` | конфигурация, данные, пользователи | резервная копия базы целиком |
| `.cf` | только конфигурация | перенос конфигурации между базами, точка возврата для конфигурации |

С файлом конфигурации в конфигураторе работают три команды меню **Конфигурация**:

- **Сохранить конфигурацию в файл** — снять конфигурацию в `.cf`;
- **Загрузить конфигурацию из файла** — **заменить** конфигурацию базы содержимым файла; данные остаются, но всё, чего нет в файле, из конфигурации исчезнет;
- **Сравнить конфигурации** и **Сравнить, объединить с конфигурацией из файла** — увидеть различия построчно и перенести выбранные изменения.

Обычный путь доработки собственной конфигурации: разработчик сохраняет `.cf` в базе разработки; в рабочей базе администратор делает `.dt`, объединяет или загружает конфигурацию из файла и обновляет конфигурацию базы данных. Если обновление меняет структуру данных, ему нужен **монопольный режим** — в это время с базой не работает никто.

## Конфигурация на поддержке

Типовые конфигурации — бухгалтерия, торговля, зарплата — разрабатывает фирма 1С или её партнёр. Такая конфигурация в рабочей базе стоит **на поддержке**: её обновляют файлами поставщика. Если компания правит типовые объекты, при каждом обновлении поставщика правки приходится объединять заново, сравнивая модули построчно. Чем больше правок в типовых объектах, тем дороже каждое обновление.

## Расширение конфигурации

**Расширение конфигурации** — отдельная конфигурация, которая подключается к основной и дополняет её, не меняя её саму. Расширение хранится в информационной базе отдельно, в файл его выгружают с расширением `.cfe`.

Что расширение умеет:

- **добавлять свои объекты** — отчёты, обработки, общие модули, роли;
- **заимствовать** объекты основной конфигурации — добавлять заимствованный объект в дерево расширения, чтобы дорабатывать его форму или модуль;
- **перехватывать процедуры** основной конфигурации с помощью аннотаций.

| Аннотация | Когда выполняется код расширения |
| --- | --- |
| `&Перед("ИмяПроцедуры")` | перед процедурой основной конфигурации |
| `&После("ИмяПроцедуры")` | после неё |
| `&Вместо("ИмяПроцедуры")` | вместо неё |

Для нашей доработки подходит `&Перед("ПередЗаписью")`: перед проверками основной конфигурации добавить свою. Если код расширения установил `Отказ = Истина`, запись будет отменена, хотя основная `ПередЗаписью` тоже выполнится.

Имена процедур и собственных объектов расширения начинаются с **префикса** — например, `Расш1_`. Так их не спутать с объектами основной конфигурации, и при обновлении основной конфигурации имена не столкнутся.

`&Вместо` — самая опасная аннотация: она отключает код основной конфигурации, и после обновления поставщика расширение может незаметно отключить новую логику, о которой не знает. Её используют, только когда иначе нельзя.

## Что выбрать

| Ситуация | Способ |
| --- | --- |
| Конфигурация своя, доработка — часть её развития | правка основной конфигурации, доставка файлом `.cf` |
| Конфигурация типовая, на поддержке | расширение: основная конфигурация обновляется поставщиком без объединения правок |
| Временная доработка или исправление, которое нужно быстро включить и легко выключить | расширение |

Учебная конфигурация — наша собственная, и в рабочей жизни правило о срочных заявках мы бы добавили прямо в модуль объекта заявки. На этом занятии мы делаем его расширением, чтобы увидеть механизм, который понадобится при работе с типовыми конфигурациями.

## Где живёт логика

| Что | Где | Почему |
| --- | --- | --- |
| Снимок конфигурации для переноса | файл `.cf` | без данных и пользователей |
| Правило «срочная заявка — с комментарием» | модуль объекта заимствованного документа в расширении | основная конфигурация не меняется |
| Порядок выполнения правила | аннотация `&Перед("ПередЗаписью")` | своя проверка добавляется, чужая не отключается |

## Что важно запомнить

1. Доработку делают в базе разработки и переносят в рабочую; рабочую базу напрямую не правят.
2. Файл `.cf` хранит только конфигурацию, `.dt` — базу целиком; загрузка конфигурации из файла заменяет конфигурацию, но не данные.
3. Конфигурацию на поддержке обновляет поставщик; правки типовых объектов приходится объединять при каждом обновлении.
4. Расширение дополняет основную конфигурацию, не меняя её: добавляет объекты, заимствует существующие, перехватывает процедуры.
5. Аннотации `&Перед`, `&После`, `&Вместо` задают, когда выполняется код расширения; `&Вместо` используют только в крайнем случае.
6. Свою конфигурацию дорабатывают напрямую, типовую — расширениями.
